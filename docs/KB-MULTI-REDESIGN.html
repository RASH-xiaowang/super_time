Design Proposal · v1

多知识库重设计：一个入口、多个库、一库一图

今天整套知识库其实只有一个隐式的库：`notes` 表一张、四个 @Remote 不带任何库标识、 [[链接]] 全库解析、图谱读全表 —— 「多个知识库」这件事在数据层根本不存在。 本次重设计把它做成一等公民的作用域：notes.kb_id 划库、每库独立的 [[链接]] 解析域与知识图谱、 每库独立的布局坐标与缓存键，侧栏入口数不变（仍 17 / 可路由 36）， 面板外壳与画布一行不改。

0一句话结论

先说结果，后面每一条都有代码出处与验证手段。

知识库 = 作用域（scope），不是第三种视图。 侧栏仍是「知识库」一个入口，顶部分段条仍是「笔记库 / 知识图谱」两段 —— 但在分段条右侧多一个库切换器；选中的库是全应用的当前作用域， 笔记库的列表与知识图谱的节点共用这一个作用域，因此「不同知识库对应不同知识图谱」 是默认行为而不是两个功能。

存储
一张表加一列
kbs(id, name, created_at, updated_at) + notes.kb_id INTEGER NOT NULL DEFAULT 1，同一个 wechat_notes.db。迁移幂等，老库零丢失。
隔离边界
按 kb_id 划三处
查询域、标题唯一域、[[链接]] 解析域。三者必须同时按库，缺一处就出现「图谱有边、列表没这篇」。
接口
kbId 必填
四个知识 Remote 的 kbId 不给默认值：漏传要能被 typecheck 抓住，不能让「忘了传」退化成「串库」。
画布
零改动
GraphCanvas / buildKnowledgeNetwork 只吃「一份快照」，快照按库取即可 —— 图谱侧不需要知道「库」这个概念。

1现状：为什么现在只能有一个库

每一条都能指到出处。注意：代码注释里其实已经写着「库内唯一」，实现却是全库唯一 —— 这次重设计就是把那句话做实。

环节现在的样子为什么这就是「单库」
存储
query/notes.ts		 CREATE TABLE notes(…) 一张扁平表，dbPath() = dirname(decryptedDir)/wechat_notes.db，没有 kb_id。 库里没有任何字段能把两批笔记分开 —— 别说切换，连「这批属于谁」都无处可写。
标题唯一 findIdByTitleKey() 用 SELECT id, title FROM notes 全表扫，归一化后比对。 两个库想各有一篇「项目组」是不可能的：第二篇会被判重名拒绝。[[链接]] 的目标名天生就是个全局命名空间。
建图
buildKnowledgeGraph()		 SELECT * FROM notes ORDER BY updated_at DESC，把全表装进 idByKey 再解析 [[链接]]。 「一库一图」在数据层无从表达：任何两批笔记只要同库文件，就必然被画进同一张网。
接口
gateway.ts		 getNotes(options?) / saveNote(options) / deleteNote({id}) / getKnowledgeGraph() —— 四个都不带库标识。 调用方就算知道「用户在看哪个库」，也没有地方把这个信息传下去。
缓存
api.ts		 内存快照键 kb:graph；渲染缓存键 kb-list / kb-graph；失效一律 invalidateWechatCache('kb-')。 键是单值的。多库共存时会出现「切到乙库，列表显示的是甲库的缓存」—— 首帧缓存是冷启动体验的关键路径，这个串库会非常显眼。
布局
graph-layout.ts		 POSITION_KEY = 'dsh-graph-layout-v1'，形状 Record<nodeId, {x,y}>，社交图谱与知识图谱共用这一张表。 两库之间节点 id 是撞的（都有 note:1 / kb:项目组）→ 切库时坐标会互相污染：甲库调好的形状会当成乙库的初值。
广播
notes-events.ts		 NOTES_UPDATED_EVENT = 'dsh-wechat-notes-updated'，无载荷；写入方只有 saveNote/deleteNote 两个入口。 事件只说明「笔记变了」，说不出「哪个库变了」。切库这件事同样需要一个信号，现在完全没有。
界面
KnowledgeBase.tsx		 顶部文案直说「存储于 wechat_notes.db（notes 表）」；空态说「知识库还是空的」。 单数语义已经写进了用户可见文案 —— 多库之后这些文案都要能说出是哪个库。

最关键的一条：注释已经许过愿

notes.ts 文件头写着「标题在库内唯一（同一归一化规则），否则 [[链接]] 的解析会产生歧义」， 而 findIdByTitleKey 的注释又说明它刻意全表取回在 JS 里比 —— 也就是说：「库」这个概念在作者的脑子里已经存在了，只是当时只有一个库，于是 「库内」 与 「全表」 恰好等价。 多库重设计要做的不是发明新概念，而是把这个已经写下但没落地的边界补上。

2目标与非目标

先用一句话钉住「多知识库」到底指什么，避免落地时各自理解。

定义

一个知识库 = 一批笔记 + 一个 [[链接]] 解析域 + 一张由这批笔记构成的知识图谱。 切换库 = 同时切换列表、图谱、布局坐标、缓存首帧；三者不可分离。

目标 ①
库之间彻底隔离
甲库的 [[项目组]] 指向甲库的《项目组》。乙库有同名笔记时互不影响，也不合并成一条边。图谱、搜索结果、标签统计同理。
目标 ②
库是可见、可切换的一等公民
能新建、重命名、删除；能一眼看出「现在在哪一库、这库有多少条」；切换不需要离开当前面板（不跳页、不重启）。
目标 ③
老数据零丢失、零感知
已有 wechat_notes.db 打开后全部落在 id=1 的《默认知识库》，标题、标签、链接、图谱结构逐字节不变。用户不新建库就感觉不到变化。
目标 ④
导航与外壳不动
不加侧栏入口（仍 17）、不加可路由页签（仍 36）、nav-config.ts 不改、GraphCanvas 不改。库管理器是弹层，不是新页。

非目标（这一版明确不做）

  • 跨库 [[链接]]：不提供 [[乙库:目标]] 这类语法。理由见 §12 —— 它是「一库一图」的直接否定。
  • 库内嵌套 / 文件夹 / 层级：库是一层平铺列表，不做树。
  • 手动排序：列表按 id ASC（创建顺序）稳定排列，不加 position 列。
  • 库级权限 / 加密 / 单独导出：同一个库文件、同一套备份路径。
  • 标签跨库共享或命名空间：标签仍是库内的自由文本（collectTags 天然跟着作用域走）。

3存储模型：kbs 表 + notes.kb_id

一个库文件、两张表、一列外键。为什么不是「一库一个 db 文件」也在这里说清楚。

3.1 为什么仍然是同一个 wechat_notes.db

  • 跨库动作变成一条 UPDATE。「把这 12 篇移进乙库」在单文件里是 UPDATE notes SET kb_id=?；分成多个 db 文件就得跨文件读—写—删，中间任何一步失败都会留下两处副本或两处丢失，而 node:sqlite 的 DatabaseSync 没有跨库事务。
  • 数据根目录保持干净。 现在数据根下已经有 wechat_tasks.db / message_edits.db 等一批 store；再按库铺开 wechat_notes_1.db、_2.db… 会让「库」的增删变成文件系统操作，备份与排查都变复杂。
  • 迁移只有一次。 加列是幂等的本地 DDL，不需要「扫描目录、导入每个文件」这种必须在用户机器上跑一次的搬运逻辑（搬运就有中断风险）。

代价也要写下来：单个库不能被单独备份/删除/移交，库文件损坏时全部库一起受损。 考虑到目标规模（每库几十到几百条、总计数千条），这个代价小于跨文件一致性的复杂度。 真要做「单库导出」，是导出成 JSON/Markdown（见 §12），而不是拆文件。

3.2 表结构

CREATE TABLE IF NOT EXISTS kbs ( -- 新增：库登记表 id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT NOT NULL, -- 唯一（normalizeTitle 归一化后） created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL ); ALTER TABLE notes ADD COLUMN kb_id INTEGER NOT NULL DEFAULT 1; -- 幂等迁移 CREATE INDEX IF NOT EXISTS idx_notes_kb -- 列表与建图都按 (kb, 时间) 取 ON notes(kb_id, updated_at DESC);

迁移的四条硬约束

  1. 必须幂等。 openStore() 每次开库都会被调到，迁移逻辑要能跑一百次而结果一致：先 PRAGMA table_info(notes) 看有没有 kb_id，没有才 ALTER。
  2. DEFAULT 1 是给老数据用的。 SQLite 的 ADD COLUMN … NOT NULL DEFAULT 1 会把既有行一次性置为 1 —— 这就是「老笔记全部落进默认库」，不需要额外的 UPDATE。仍要补一条 UPDATE notes SET kb_id=1 WHERE kb_id IS NULL 兜住历史脏值（防御性，正常查不到行）。
  3. 保证 id=1 一定存在。 迁移末尾：若 kbs 里没有 id=1，插入《默认知识库》。无论有没有笔记都要插 —— 新用户第一次打开就必须有一个「当前库」，否则界面要面对「没有作用域」这个不该存在的状态。
  4. 默认库不许被删。 id=1 视为系统库：可改名，不可删除（deleteKb 直接拒），避免「迁移兜底逻辑」每次开库都复活一个空库、或者用户删光后陷入无库状态。

3.3 唯一性的作用域变化

约束现在改成
笔记标题唯一 全表（findIdByTitleKey 扫全表） 库内唯一：扫 WHERE kb_id = ?。同一库内仍拒绝重名（[[链接]] 不能有歧义），跨库允许同名。
库名唯一 — 全局唯一（同一套 normalizeTitle），错误文案沿用既有风格：已存在同名知识库「X」。空名拒绝：知识库名不能为空。
[[目标]] 解析 全表 idByKey（首见者胜） 只在本库内建 idByKey；库外同名笔记既不成边、也不出现在 stub 提示里（跨库提示是只读探针，见 §8.7）。

3.4 建议的签名（后端）

// 迁移 + 常量都在这一处 —— 别在别处硬编码 1 export const DEFAULT_KB_ID = 1 export const DEFAULT_KB_NAME = '默认知识库' export function listKbs(decryptedDir: string): KbListSnapshot // 带每库 noteCount export function createKb(decryptedDir: string, name: string): KbMutationResult export function renameKb(decryptedDir: string, id: number, name: string): KbMutationResult export function deleteKb(decryptedDir: string, id: number, action: { kind: 'reassign'; targetKbId: number } | { kind: 'purge' }): KbMutationResult // 四个既有函数一律把 kbId 提到第 2 位（必填、位置参数）—— 漏传即 typecheck 报错 export function listNotes(decryptedDir: string, kbId: number, options?: { query?: string; limit?: number }): NotesSnapshotRead export function saveNote(decryptedDir: string, kbId: number, input: { … }): NoteMutationResult export function deleteNote(decryptedDir: string, kbId: number, id: number): NoteMutationResult export function buildKnowledgeGraph(decryptedDir: string, kbId: number, names: Map<string, string>): KnowledgeSnapshotRead

为什么 kbId 必须是必填的位置参数

可选参数 + 隐式默认值是最舒服的写法，也是最危险的：任何一个忘了传 kbId 的新调用点，都会静默地操作默认库 —— 表现为「保存成功但列表里没有」「删了别的库的东西」，而 typecheck、build、SSR 冒烟全都不会报。 本项目已经在这个模式上吃过一次亏（问卷额度：任一侧自写整数 → 「模型里有边、图上没画」）。 所以规则与 graph-budget.ts 同款：边界只有一处定义，两处使用都必须显式传参。

4作用域契约：五处必须按库分

这张表是本次重设计的核心不变量。五处里漏掉任何一处，症状都不是「少个功能」，而是串库。

层键 / 参数现在改成
数据
SQL		 WHERE kb_id = ? 无 取列表、取图谱、删、查重全部带 kb_id；UPDATE 的 WHERE 也必须带（否则改一条会串改同 id？—— id 是主键，但带上是纪律：任何 WHERE 都不能只有一个 id，防止未来改成批量更新时静默扩大范围）。
接口
Remote		 kbId 显式参数 四个 Remote 都没有 四个知识 Remote 全部加 kbId；新增四个库管理 Remote（getKbs / createKb / renameKb / deleteKb）。getKbs 与 deleteKb 是唯二不带 kbId 的（前者是全局列表，后者用 id 指定）。
缓存
内存		 cachedGet('kb:graph:' + kbId) cachedGet('kb:graph') 键后缀库 id。apiGetNotes 依旧刻意不走缓存（搜索框每敲一个字都要最新结果），这条注释里的理由与库无关，保持不动。
缓存
渲染层		 kb-list:<id> / kb-graph:<id> kb-list / kb-graph 加库后缀。库登记表自己的缓存用 kbs-list（不以 kb- 开头）。KnowledgeBase.tsx 里那段「key 必须带 kb- 前缀，否则图谱刷新了列表还是旧的」的注释仍然成立 —— 只是键多了一段。
布局
localStorage		 scope = 'kb:' + kbId
或 'social'		 单键 dsh-graph-layout-v1 扁平表 新键 dsh-graph-layout-v2，形状 Record<scope, Record<nodeId, {x,y}>>；loadSavedPositions(scope) / savePositions(scope, pos)。旧的 v1 只读回退（见 4.2）。

4.1 「作用域」只有一处定义

与「额度只有 graph-budget.ts 一处」同一条纪律：新增前端模块 panels/kb-scope.ts，导出

  • kbScope(kbId) → 'kb:' + kbId，SOCIAL_SCOPE = 'social'；
  • POSITION_SCOPES_MAX = 8（见 4.3）；
  • 当前库的读写与订阅（useKbScope()、setActiveKb()）。

铁律：任何地方不得再手写 'kb:' + id 或 'kb-list:' 字面量。 由源码级用例守住（grep 整个 wechat-data/**，只允许 kb-scope.ts 出现这些字面量）—— 这比运行期断言可靠：字符串拼错不会抛错，只会静默用另一个键，也就是静默串库。

4.2 布局坐标的迁移：只读回退，不改写

// 读：v2 命中就返回；否则回退到 v1 的扁平表（仅限两个 scope） loadSavedPositions(scope): v2 = 读 dsh-graph-layout-v2 → 命中 v2[scope] 即返回 否则若 scope ∈ { 'social', 'kb:1'(默认库) }: 返回 v1 的扁平表（不写入 v2，下一次落盘自然升级） // 写：永远只写 v2[scope]，并把该 scope 移到 LRU 首位 savePositions(scope, pos): v2[scope] = pos; v2.__lru = [scope, …去重]

为什么不把 v1 摊进每个库的 scope：v1 里混着社交与知识两套坐标（靠节点 id 不重叠才没打架）， 若按库复制，6000 条坐标 × N 个库会直接撞 localStorage 配额；而回退读只在首次生效，代价为零。 为什么不删除 v1：它是用户上一次调好的形状，删掉等于让老用户的所有库都重新布局一次； 回退是只读的，留着不占额外空间。

4.3 配额：作用域上限与 LRU

GraphCanvas 已有 POSITION_CACHE_MAX = 6000（单图上限）， 多库之后总占用变成 6000 × 库数，而渲染进程的 localStorage 里还住着消息缓存 —— 真机实测过它会被占满、setItem 抛 QuotaExceededError（savePositions 已有「打一次日志」的降级）。 因此再加一条：v2 最多保留 POSITION_SCOPES_MAX = 8 个作用域，超出按 LRU 淘汰最久未写的一个。 淘汰的代价只是「那个库下次进入重新布局」，不会丢数据（笔记在主库、不在 localStorage）。

4.4 节点 id 保持不变（重要）

一个直觉的改动是把 stub 节点 id 也加上库前缀（kb:2:项目组），因为「两库都有同名 stub 会撞」。 不采用：布局整体按作用域隔离之后，同一份 map 里根本不会同时出现两个库的节点， 而节点 id 还被三处消费 —— graph-model.ts 的边端点、Graph.tsx 的选中/固定/深链、 以及已有的一批 graph-model.stub.spec.ts 断言。 改 id 是把风险从「一个键」扩散到「三处消费 + 一批用例」，而收益是零。

5后端接口变化

四个改签名、四个新增。签名改动是这次重设计唯一有编译期保障的护栏，所以要做彻底。

Remote签名说明
getNotes
改		 (options: { kbId: number; query?: string; limit?: number }) kbId 进 options（Remote 的既有风格就是单 options 对象）。total 必须改成本库计数（现在是全表 COUNT(*)）—— 不改就会显示「12 / 37」这种跨库总数。
saveNote
改		 (options: { kbId: number; id?: number; title: string; … }) 新建时写入该 kb_id；编辑时也必须带 kbId 并校验行确实属于该库（WHERE id=? AND kb_id=?，不匹配返回 笔记不存在）—— 这是防串库的最后一道。
deleteNote
改		 (options: { kbId: number; id: number }) 同上：删除也要 AND kb_id=?。返回 ok:false 时前端已有「删除失败」路径，无需新状态。
getKnowledgeGraph
改		 (options: { kbId: number }) 建图只读本库。sessionNames（问答来源会话显示名）也只会包含本库涉及的会话 —— 天然收敛，无需额外处理。
getKbs
新增		 () 返回 { items: KbMeta[], total }，KbMeta = { id, name, noteCount, createdAt, updatedAt }。noteCount 用一次 GROUP BY kb_id 拿全，别在循环里查。顺序固定 id ASC。
createKb
新增		 (options: { name: string }) 返回 { ok, id }。归一化重名拒绝。名字 trim 后长度上限 40（超出拒绝而不是截断 —— 截断会让用户看到的名字与他输入的不一致）。
renameKb
新增		 (options: { id: number; name: string }) 默认库可改名。改名不影响任何笔记（笔记不存库名，只存 kb_id）—— 这正是用外键而不是「以库名为键」的理由。
deleteKb
新增		 (options: { id: number; action: { kind:'reassign'; targetKbId:number } | { kind:'purge' } }) 必须显式给出非空库的处理方式，后端不猜。reassign 在一个事务里 UPDATE notes SET kb_id=target WHERE kb_id=? 再删库行；purge 直接删笔记再删库行。id=1 一律拒绝。

类型要改三处，别只改一处

  • src/backend/wechat-data/src/types.ts：KnowledgeNote 加 kbId；新增 KbMeta / KbListSnapshot / KbMutationResult。
  • api.ts 里的 Remote 接口声明（getNotes / saveNote / deleteNote / getKnowledgeGraph 四条 + 四条新增）—— 这份是不走代码生成的、必须手改，漏改会退化成 any 风格的静默错误。
  • 前端 wechat-data/types.ts：按既有说明刻意再声明一份（不从 node_modules 那份旧副本引入），同步加 kbId 与新类型。

7交互与空态

多库之后「空」至少有四种含义，必须句句不同 —— 这是上一版知识库用 N1 换来的一条经验。

场景文案动作
库里确实没有笔记 「工作笔记」还没有条目
手写笔记与「微信问答」的沉淀都进这个库，正文可以用 [[目标]] 互相链接。		 ＋ 新建第一条（在原库内新建，不再问库）
库读不到（库被占用/损坏） 「工作笔记」读取失败（不是「暂无条目」）：<原因> 重试；不写渲染缓存（现有 N1 规则：把读失败的空表写进缓存，下次打开会伪装成「库里没东西」）
筛选后为空 没有匹配的条目 + 当前条件：关键词「x」· 标签 #y 清除筛选（保持现状）

7.1 切换库时的三个可见承诺

  1. 不跳页、不重挂面板。 切库只改作用域 → 两个面板各自重取数据；分段条（笔记库 / 知识图谱）停在原地。
  2. 首帧不串库。 因为渲染缓存的键里带库 id，切到乙库时读的是 kb-list:2：有缓存就先出乙库的内容，没有就出骨架屏 —— 永远不会先闪一下甲库的列表。
  3. 布局按库恢复。 切换回来还是上次的形状（scope 隔离 + v2 键）。

7.2 问答沉淀（Ask 面板）

Ask.tsx 里「沉淀为笔记」打开同一个 KnowledgeNoteEditor（sourceKind="ask"）。 多库之后它必须回答「存到哪个库」：默认=当前作用域，编辑器内可见并可就地改。 这样从问答沉淀而来的笔记也会自然成为某个库图谱里的一个节点，而不会出现「沉淀了但不知道进了哪个库」。

8边界与失败模式

十二条。每一条都写成「触发 → 期望行为」，落地时可以直接变成用例。

#触发期望行为
1老库升级（无 kb_id）全部笔记落进 id=1《默认知识库》，标题/标签/链接/图谱结构不变；kbs 若为空则建默认库。迁移跑两次结果一致（幂等）。
2老库的布局（v1 单键）social 与 kb:1 两个作用域可读到它；其他库从确定性初值开始。v1 不被改写、不被删除。
3删除非空库弹层列出条数，必须二选一：移到…（目标库选择器） 或 一并删除。没有「直接删」这个默认路径，后端 deleteKb 也不给缺省 action。
4删除当前库作用域确定性地退回「列表里第一个剩下的库」（id ASC）；若一个都不剩 → 自动创建《默认知识库》并选中。**界面永不停留在无库状态。**
5删除 id=1拒绝（默认知识库不可删除，可重命名）。理由见 §3.2 第 4 条：它同时是迁移兜底。
6库重名 / 空名 / 超长重名 → 已存在同名知识库「X」；空名 → 知识库名不能为空；>40 字 → 拒绝并提示（不静默截断）。
7两库有同名笔记各自独立：互不成边、互不覆盖。详情页对 [[目标]] 未命中时，可给一条只读提示「其他库里有同名条目」+「在那里打开」（跳转时切换作用域）—— 但这绝不自动建边。
8保存/删除时 kb_id 不匹配返回 笔记不存在（WHERE id=? AND kb_id=? 改不到行）。前端已有「保存失败」路径可展示。
9两个窗口开着不同库各自独立（作用域在渲染进程内存 + localStorage）。已知限制：A 窗口在甲库改笔记，B 窗口在乙库不会看到 —— 但 B 会因 NOTES_UPDATED_EVENT 重载自己的库，取到的是正确（只是无关）的数据。文档里写明，不做跨窗口同步。
10localStorage 配额满savePositions 已有的降级：只打一次日志、不抛。再加 scope LRU（上限 8）压低总占用。表现=「下次进入不恢复布局」，不丢笔记。
11迁移中途失败（ALTER 被拒等）openStore 的既有策略：建目录失败仍继续尝试打开；读失败由 listNotes 转成 readError 的空快照。迁移失败不能伪装成空库 —— 迁移异常要进 readError 文本，并且不能把空 kbs 列表当成「没有库」（否则会新建一个空库盖住现场）。
12库列表读取失败getKbs 失败 → 保留上一次列表（内存）并给一次可重试的提示；作用域保持原值。等价于「不敢猜你在哪个库」。

12明确不做，以及为什么

每一条都是看起来合理、但会伤到别处的东西。留在这里，避免下次又绕回来。

① 跨库 [[链接]]（[[乙库:目标]]）

最诱人的功能，也是最该拒绝的。「一库一图」的定义就是「图只由这一库的笔记构成」： 一旦允许跨库边，知识图谱就会退化成「全库图 + 一堆指向虚空的边」—— 而 stub 机制（kb:<目标名>）正是靠「目标不存在就先记成待补」来表达「这条链接活着但还没写」， 跨库边会让「该在哪个库补」变成第二个需要猜的问题。 替代方案已给：未命中时只读提示「其他库里有同名条目」+ 一键跳过去（跳转即切库），信息不丢，隔离不破。

② 一库一个 db 文件

好处是「单库可单独备份/删除」，代价是跨库移动笔记要跨文件读写， 而 node:sqlite 的 DatabaseSync 没有跨库事务 —— 中途失败会留下两份副本或两份丢失。 真需要单库出口，应当做成导出（JSON / Markdown，带 [[链接]] 原样）， 那是只读且不会破坏一致性的一步。

③ 把库做成第三个分段（笔记库 / 知识图谱 / 库管理）

分段表达的是「同一份数据的两种看法」，而库表达的是「看哪一份数据」——是上一层的维度。 两者并列会诱导出「在甲库里点知识图谱」这种语义矛盾。 所以库选择器放在分段条右侧（作用域位置），库管理做成弹层。

④ 给笔记加「多库归属」（一篇属于多个库）

多对多立刻把「标题库内唯一」和「[[链接]] 解析域」两个不变量同时打穿： 同一篇笔记在两个库里要有两个不同的解析上下文，图谱也会把它算两个节点。 多库的价值在分类，而分类需要唯一归属。要复制，就用「复制到另一个库」（会产生新 id 的新笔记，两库各自独立演进）。

⑤ 用库名做外键（而不是 kb_id）

用库名做键会导致「改名 = 迁移全部笔记」，并且要处理「改到一半崩了」。 用 kb_id 之后改名是一条 UPDATE、零笔记改动（§5 里 renameKb 的说明）。 库名唯一性只用于防呆，不承担引用职责。
