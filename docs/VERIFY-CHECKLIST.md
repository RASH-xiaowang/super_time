> 技术细节、逐接口前后对照、已排除的假设、测量陷阱等全部在
> [`PERF-THEME-LEDGER-2026-09-29.md`](PERF-THEME-LEDGER-2026-09-29.md)。本文件只回答

```bash
npm run verify:all
```

**期望**：末尾打印六行 `PASS`，且以"全部通过"结束。它分三层：

| 层 | 查什么 |
|---|---|
| ① 产品 | 类型检查 · API.md 与源码一致 · 全量 3923 个用例 · 真机界面 |

## 1. 我想确认"接口变快了"

```bash
python working/run-probe.py probe-remote.ts
```

（本地探针，需本机有解密数据；`working/` 不入库）

**期望**：
- `完全调通（无错误）: 168–171 / 174` —— **区间取决于探针超时**：默认 4s 下是 168–170
  （5 个长任务被记成 `TIMEOUT`），把超时放到 180s 再跑是 171（`SUPERTIME_PROBE_TIMEOUT_MS=180000`）
- `成功或仅超时：171–173 / 174`
- **「让出 0 且冷跑 >50ms」**：3–5 个，且**全部 ≤ 150ms**

**关键判读** —— ⚠️ 这里有个**容易看错的地方**，先说清：

| 口径 | 修前 | 今天 |
|---|---|---|
| **≥200ms 的整段独占**（当时那批"真要等"的） | **6 个，最长 228ms** | **0 个** |
| **>50ms 的整段独占**（含 50ms 线附近的抖动项） | 6 个 | **3–5 个** |

账本里写的"**6 → 0**"指的是**上面那行**（≥200ms 那批确实全部消失）。
今天列出的 3–5 个是**下一行**：全在 150ms 以内，且逐个查过来源
（`autoGetDbKey` 是读微信进程内存、`autoGetImageKey` 早已修过只是走了快路径、
`askWechat` 是 LLM 路径、`listBackups`/`exportSessionMessages` 压在 50ms 线上浮动）。

⇒ **要看的不是"个数是不是 0"，而是"有没有 ≥200ms 的"**。
50ms 线附近的项会随轮次在 3–5 间浮动，**那是噪声，不是回归**。

**不成立意味着**：又出现了 ≥200ms 的长独占项（真回退），或整批接口普遍变慢。

## 3. **需要你亲眼看的一件事**（我做不到）

**浅色主题的观感只能人工确认。** 原因不是没写检查，而是**截图在本环境不可信**：
实测同一时刻截图显示"骨架屏 + 首次配置向导"，而同进程的 DOM 探针报 `nm-skel=0`、无对话框。
截图受时序/合成影响，**不能当判据**，所以自动化只能停在 computed style。

**怎么做**：

```bash
# ① 深色截图（16 个主导航页签 + 20 个隐藏页签）
npm run ui:panel-audit

# ② 浅色截图 —— **这一步是你要看的那份**（2026-09-29 新增）
node scripts/panel-audit.mjs --theme light
```

浅色图写成 `<页签名>.light.png` / `hidden-xxx.light.png`，与深色图**并列落在**
`.tmp-e2e/panels/` ⇒ **同一页签的深浅两张可以直接对着看**。

> 页签口径：主导航**实测 16 个按钮**（`data-testid` 之外按按钮标签数过一遍）；
> `nav-config.ts` 里另有 20 个 `hidden: true` 的页签，由各面板的「详情 →」或 hash 进入。
> 合计 36 张/主题。（`nav-config.ts` 里 `tab:` 条目共 37 —— 多出的那个是**设置**齿轮，不是导航按钮。）

> `--theme light` 会**先断言主题真的切过去了**（读 `htmlClass`），否则直接报错退出 ——
> 免得产出"看着像浅色、其实是深色"的截图被当成证据（第 16 轮踩过这个坑）。

⚠️ **看浅色截图时注意三件事**（2026-09-29 实测，免得你误判）：

1. **窗口顶部的外壳是深色的**，且截图里还带着两条测试态横幅（红色"验收测试模式"、
   紫色"调试模式"）。**那部分是主进程外壳，不随主题变**，不是缺陷。
2. **`数据总览` 用的是霓虹皮肤**（`overview-neon.module.css`）：**2026-09-29 已修好** ——
   它的 13 条浅色规则原先写的是裸 `:root.theme-light`，被 CSS Modules 哈希成
   `:root._theme-light_…`，而 `<html>` 上是原样的 `theme-light` ⇒ 选择器永不匹配、
   整段覆盖是**死规则**，于是浅色下卡片/指标条/牌面仍是深海军蓝（这就是当时的报障）。
   现在改成属性选择器 `:root[class~='theme-light']`（属性值不参与 CSS Modules 哈希，且本目录禁止
   用 `:global(.局部类名)` 跨模块覆盖）：浅色下实测卡片是 **`linear-gradient(158deg, rgba(255,255,255,.9), rgba(244,248,252,.84))`（白玻璃）**，
   页底 `rgb(255,255,255)`，深色下仍是深蓝紫玻璃。
   同一排**指标牌**还有两层要一起看（同日修）：内嵌玻璃面 `.plateFace::after` 必须换浅玻璃（否则白底被深玻璃盖住），
   `.plateValue` 的浅色规则**必须重新声明 `background-clip: text`**（`background` 简写会把它重置，数字会隐身只剩一条渐变条）。

3. **那 4 个 `hidden-*`（`hidden-health` / `hidden-hook` / `hidden-privacytrust` / `hidden-backup`）
   是「设置」弹窗**（`scripts/panel-audit.mjs:292-293` 注明）。**已实测**：浅色主题下遮罩是
   `_dialogOverlay_1uop3_159` = **`rgba(4, 8, 20, 0.6)`** —— **半透明 0.6，且刻意不随主题变**
   ⇒ 弹窗后面的背景自然偏暗。**不是缺陷。**

**已验证的硬事实**（computed style，非肉眼、也非像素采样）：

| 元素 | 深色 | 浅色 |
|---|---|---|
| `body` 背景 | `rgb(5,10,24)`（均值 13） | `rgb(246,248,251)`（均值 **248**） |
| `数据总览` 内容区不透明底色（12 个采样点） | 深色 | **全部 `rgb(255,255,255)`** |
| `--nm-text-1` | `rgb(226,232,240)` | `rgb(15,23,42)` |

> ⚠️ **别用"截图像素统计"当判据**：我试过按亮度自动挑"最可疑的页签"，
> 结果把霓虹皮肤的深色卡片、弹窗遮罩全算成了"背景仍偏暗"的嫌疑 —— **全是假阳性**。
> 判颜色要看 **computed style**；截图只适合**人眼**看"像不像"。

看这两件事：

1. 有没有"**深底配浅字**"或"**浅底配白字**"的区块（看不清楚）；
2. 有没有明显的**颜色不一致**（同一类元素在不同页面深浅不一）。

**如果发现问题**：把出问题的**页签名 + 大致位置**告我即可，我按 `path:line` 定位。

**已量化的事实（供参考，不替代肉眼看）**：**正文类**文字在 36 个页签 × 2 套主题下
**全部 ≥ 4.5**（WCAG AA，真机多采样，最低 4.51）；低于 AA 的只有两处，且都是
**微信官方色值的保真取舍**、已按棘轮登记：
① 深色端弱化文字 `--nm-text-3` 3.75–4.15（`ui/kit.module.css:34-37` 已记录）；
② 未读徽标白字压官方红 `#FA5151` = **3.30**（两套主题同值）。

## 4. 已知限制（不是缺陷，列出来免得你重复排查）

| 现象 | 性质 |
|---|---|
| 深色端弱化文字 `text-3` 3.75、未读徽标白字压官方红 3.30 | **已登记的有意取舍**（复刻微信官方色值），按棘轮只许不变差 |
| 先连续点过约 10 个以上页签，再点 `朋友圈`/`收藏与表情`，要等约 60 秒 | **已定性**：这两个面板会让后台 worker 进入持续满负荷（与页面无关、不自行结束）；7 个假设已逐个用实验排除，根因未定位；**有门禁**（`--stress`）在管 |
| 连点页签时面板审计变慢（12 秒/屏 → 1 分钟/屏） | 同上，worker 被打满的副作用 |
| `analyzeMessages` 有 2550ms 片段 | 已定性为 **ONNX 推理本身**（同步、不可中断）；仓库已实测否决过批处理（合批慢 41.8%） |
| 20–45ms 的接口仍有一次不让出的 | **有意不动**：串行 worker 上用户感知不到，逐个改造的跨模块成本大于收益 |
| 全量用例偶尔红一两条 | 工作树里有**他人未提交**的改动；`verify:all` 会自动重试并区分"间歇"与"真坏" |
