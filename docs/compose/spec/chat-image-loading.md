# 聊天图片加载流程（性能与占位体验）

- 日期：2026-09-26
- 触发：用户截图 —— 一个会话里 8 条图片消息同屏，整屏都是「图片加载中…」
- 相关守卫：`panels/image-loading.wiring.spec.ts`（8 条，变异八处全咬）、
  `image-cache.spec.ts`（8 条 LRU 语义单测）

## 1. 问题

截图里能同时看到两类事实：

1. **每条图片消息都要先闪一次文字占位**（`<IconImage /> 图片加载中…`）——图片密集的会话里，
   整屏都是那句话，而它其实什么信息也没有。
2. **同一屏 8 张图一起卡在加载态**，只有一张已经是真图（那张是本机早就有更大的解码产物、
   命中后端磁盘缓存的）。

## 2. 现状盘点（改之前就有的东西）

| 环节 | 现状 | 结论 |
|---|---|---|
| 后端解码 | 产物落 `<decoded>/<username>/<md5>.<ext>`，单张入口优先读它 | 磁盘缓存已有 ✓ |
| 批量入口 | `getImageDataUrlsBatch`：一次 `IN (...)` 查完整批 md5 的 `.dat` 路径并预热解码 | 已有，但消息流没用它 |
| 前端合并 | `image-batch.ts` 把**同一个 tick 内**的多次取图合并成一次批量 RPC | 只在「一次提交里挂 N 个组件」时有效 |
| `<img>` | 已带 `loading="lazy"` | 原生 lazy 管的是**解码**时机，管不了**取数**时机 |

**真正的两个缺口**：

- **没有跨挂载的内存缓存**。图片消息是虚拟化列表里的一行：滚出视口 → 组件卸载 → 组件内的
  `src` 状态一起消失；滚回来 → 重新挂载 → **重新走一次 RPC**（后端虽命中磁盘，仍有一次
  进程间往返 + 读盘 + base64 编码）。用户看到的就是「每次滚回来都先闪一下占位」。
- **没有预取**。取数时机完全由「这一行进入视口」触发 —— 也就是说，**用户看到占位的那一刻
  才开始取**，占位是必然出现的，不是偶发。

## 3. 方案（四层）

### 3.1 缓存层：`image-cache.ts`（按字节计的 LRU）

- key = `username:localId`（会话 + 消息双重定位，换会话不串味）。
- **按字节计容量**而不是按条数：一条 data URL 的体量差三个数量级（缩略图几十 KB、原图
  base64 好几 MB）。按条数计在遇到一批原图时会吃掉几百 MB。
  - 总量上限 `MAX_BYTES = 48MB`（一屏缩略图约 3–5MB，够来回滚十几屏）；
  - 单条上限 `MAX_ENTRY_BYTES = 8MB`：**超过就不缓存**（一张原图不该把一整屏缩略图挤出去）。
- **只缓存成功结果**：失败/空 url 不进缓存 —— 「这次没取到」不能被记成「已知没图」。
- LRU 用 `Map` 的插入序实现（命中即 `delete` + `set` 移到队尾），不需要双向链表。

### 3.2 预取层：`use-image-preload.ts`（可见窗口 + 余量，低优先批量）

- 收集**可见窗口上下各 `LOOKAHEAD = 8` 行**里的图片消息（虚拟化器给的可见区间 ± 余量），
  过滤掉已缓存 / 在飞的，然后**批量**取回并写缓存。
- 走 `getImageDataUrlsBatch` 而不是逐张：后端单张入口每图都要开合一次库
  （`WHERE lower(md5) = ?` 在 `image_hardlink_info_v4` 上是全表扫，实测 20 万行 17.27ms/次），
  批量入口一次 `IN (...)` 就把整批路径查完。预取天然是「一批」场景。
- **空闲调度**（`requestIdleCallback`，无则退化为 250ms 延时）+ **滚动防抖 150ms**：
  视口内那几张是用户此刻正看着的，必须优先；预取不能与它抢后端解码进程与 IPC 通道。
- 跨 effect 重跑去重（滚动会不停重跑）+ 换会话作废在途（`epoch`）。
- **预取失败静默且不写缓存**（下次滚到还会再试）；组件自己那条路径相反 —— 那是用户正看着的
  图，失败必须说话。

### 3.3 展示层：骨架 + 慢提示 + 淡入

- 占位从「图标 + 图片加载中…」换成**定尺寸骨架**（`160×120`，取 `.msgImage` 区间 96–240
  里的常见值）+ 呼吸动画。骨架表达同一件事（还在取），但不占阅读注意力。
- **默认一个字的文字都没有**；只有超过 `SLOW_MS = 2500ms` 还没回来才补一句「加载较慢…」
  —— 弱网下需要知道「它在努力」，正常网络下这句话永远不出现。
- 图片就绪后 `data-loaded` 触发 150ms 淡入，抹平「骨架 → 图片」的突变。

### 3.4 优先级与分工

| 场景 | 走哪条路 | 优先级 |
|---|---|---|
| 视口内的图（用户正看着） | `apiGetImageDataUrl`（经 `imageLoadQueue` 同 tick 合并） | 高（立即） |
| 视口上下 8 行内的图 | `apiGetImageDataUrlsBatch`（本 hook） | 低（空闲） |
| 滚回来 / 切回会话 | **内存缓存命中，不发任何请求** | — |

两条路径写**同一个缓存**，谁先回来都算数 —— 所以不会长期并存重复请求，也不会因为预取失败
而让图片出不来。

## 4. 弱网下的表现

- 骨架常驻 → 布局不跳（尺寸固定），用户看到「在取」而不是「坏了」；
- 2.5s 后出现「加载较慢…」这句弱文案；
- 取不到（解码失败 / 本机无更大产物）走原有的错误分支：显示**具体原因**
  （`hevc-unsupported` / `找不到 .dat` / …）与「取原图」按钮，不静默；
- 原图取回后写入 `<decoded>/`，**下一次渲染直接是原图**、之后离线可用（网络只花一次）。

## 5. 顺带补的一处类型事实

`getImageDataUrlsBatch` 的后端实现是
`{ username, localId, ...decodeImageDataUrl(...) }`，而 `decodeImageDataUrl` 返回的就是
`ImageDataUrlResult`（**含 `thumb`**）—— 也就是说运行期数据一直有它，只是
`ImageBatchItem` / `ImageDataUrlBatchItem` 两份类型没声明。预取要把结果写进缓存，
缓存里少了这个标记，「本机只有缩略图」那句提示会在命中缓存时凭空消失。
所以本轮把 `thumb?: boolean` 补进两份类型（**不是新增行为，是把已有事实写下来**）。

## 6. 未做 / 已知边界

- **骨架与真实图片的尺寸可能不一致**：后端结果里没有图片宽高（`ImageDataUrlResult` 只有
  url/format/thumb/error），所以骨架用固定 `160×120`，加载完成时会有一次高度调整。
  要彻底消除需要让解码链路顺带返回尺寸（后端改动，本轮未做）。
- `MessageImageGroup`（多图合并的一组）与 `ImageViewer`（大图查看器）**也走同一份缓存**
  （它们调 `apiGetImageDataUrl`），但只有 `MessageImage` 改了占位形态。
- 缓存没有持久化：刷新应用即空（磁盘层由后端的 `<decoded>/` 承担）。
