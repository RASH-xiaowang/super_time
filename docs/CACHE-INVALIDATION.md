# 缓存失效的四条通道（2026-09-29 沉淀）

> 这份文档是"用血换来的"：连续多轮把同一条目标（提高每个界面取数速度）往下做时，
> **每一轮都栽在缓存失效上**。四条通道看起来都像"同一个 bug 又出现了"，实际各自独立，
> 修法也不同。写在这里，免得下一个人（或下一个我）再花几轮去重新发现。

## 通道 ①：签名精度不够（`mtimeMs`）

- **现象**：数据变了，缓存却回旧值。
- **机理**：签名 = `mtimeMs + size`。SQLite 文件**页对齐**，插入一条小记录**不改 size**；
  写入又可能落在**同一毫秒**里 ⇒ 签名看起来没变。
- **修法**：改用 `statSync(path, { bigint: true }).mtimeNs`（NTFS 100ns 精度）。
- **成本实测**：2 万次 `statSync`，普通 **8.30µs** vs bigint **8.35µs** ⇒ **不花成本**。
- **落地**：`meta.ts`（`fileSig`/`dirSig`）、`vector-math.ts`（`statSig`）、`files.ts`（两处）。

## 通道 ②：看错了文件（WAL）

- **现象**：同上，但在 WAL 模式下更隐蔽。
- **机理**：SQLite 默认 WAL，**写入先进 `<库>-wal`**，主库的 mtime/size 可能一直不变
  （直到 checkpoint）。
- **修法**：签名拼上 `:<wal mtimeNs>:<wal size>`；没有 `-wal` 时回落成空串（行为不变）。
- **落地**：`meta.ts` 的 `walSig()`。

## 通道 ③：在飞表没有按签名分桶

- **现象**：数据变了（签名 B），新调用却拿到**旧值**。
- **机理**：`cachedBySigAsync` 的去重表原先**只用 `key`**：
  新签名调用会 `return running.value`，而那是**旧签名 A** 那次计算的结果。
  这条与①②方向相反：①②是"变化看不见"，这条是"**看见了变化，却被在飞的旧计算顶掉**"。
- **修法**：`flightKey = key + '\0' + sig`。同签名仍共享一次计算，签名不同各算各的。
- **落地**：`meta.ts` 的 `cachedBySigAsync`。

## 通道 ④：`mtime` 本身不可靠（NTFS 懒刷新）——**已解决（第 20 轮）**

- **现象**：写入并 `close()` 之后，`stat` 报出来的 mtime **完全没变**（连纳秒都一样）。
- **机理**：**Windows/NTFS 对"最后写入时间"是懒刷新的**。与精度无关，与看错文件也无关。
  定案证据（`SUPERTIME_CACHE_TRACE=1` 打点）：
  ```
  [算料|sig] 插入前=1790678154940830600:20480  插入后=1790678154940830600:20480
  [cache-trace] hit storage-stats:… sig=1790678154940830600:20480…
  ```
- **曾经的结论**（"stat 堵不住，要改用 `PRAGMA data_version` 且需要长连接"）**已被更好的办法取代**：
- **✅ 修法：把 SQLite 的「文件变更计数器」读进签名**。SQLite 格式规范规定：数据库文件每次被
  修改（**包括 WAL checkpoint**）都会把**头部偏移 24 的 4 字节计数器自增**。读它
  **与文件时间无关**，因此不受懒刷新影响；只要**开→读 32 字节→关**，不需要连接、不需要查询。
  实测插入前后：`…:20480:12` → `…:20480:14`（size 一样、mtime 甚至可能没变，计数器一定变）。
- **成本实测**：2 万次 —— `statSync(bigint)` **8.70µs** vs `开+读32B+关` **9.10µs**
  ⇒ 每次签名多 **~0.4µs（5%）**，可忽略。
- **落地**：`meta.ts` 的 `sqliteChangeCounter()`（先验头部魔数 `SQLite format 3`，
  非数据库文件返回空串，避免给图/视频/JSON 引入无意义抖动），接进 `fileSig`
  ⇒ **所有 `cachedBySigAsync` 调用者**（storage / wordcloud / sessions / moments / …）都受益。
- **副产品**：那条用例**不再需要 `utimesSync` 这个测试侧的拐棍**，
  回到"真的写了一条数据 ⇒ 必须重算"的原始契约；连跑 6 次全绿。

## 写测试时的规矩（这三条已经各咬过一次）

1. **用例要验的契约是"签名变了 ⇒ 必须重算"**，所以用例必须让"签名确实变了"这个前提成立
   —— 不要假设"写一行数据就会改 mtime/size"（通道④）。
2. 构造"确实变了"的写入：**显式 `utimesSync` 推到未来**（并注释为什么）；
   或者用共享助手统一推（见 `kb-vectors.spec.ts` 的 `buildBumped()`）。
3. **不要逐条打补丁**：同一机理往往在一个文件里多处出现。先在一条上定案，
   再用一处根因（共享助手 / 公共口径）治整族 —— `kb-vectors.spec.ts` 25 个调用点就是这么治的。

## 诊断工具（本仓已有，别再临时造）

- `SUPERTIME_CACHE_TRACE=1`：`cachedBySigAsync` 每次决策打 `hit/miss + 新签名 + 旧签名`
  —— 通道④就是靠它一轮定案的。
- `SUPERTIME_SNS_TRACE=1` / `SUPERTIME_COVER_TRACE=1`：分段计时与分层命中计数。
- `SUPERTIME_SLOW_CALL_MS=<ms>`：把"慢调用"日志阈值从 1000ms 调低，拿逐接口时间线。
- `working/watch-decoded-dir.mjs`：递归盯目录，抓"谁在什么时候把缓存删了"。
