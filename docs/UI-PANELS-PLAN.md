# Super Time 功能界面完善计划

> 来源：2026-09「微信数据总览」重设计之后，把同一套方法与口径推广到**其余全部功能界面**。
> 用途：**界面完善的任务计划与实施跟踪**。每条都有稳定 ID、优先级与可执行的验收标准。
> 与 `RELEASE-PLAN.md` 的关系：那份是上线总计划（架构/安全/性能），这份只管界面。

---

## 一、方法论（为什么这样定计划）

### 1.1 界面问题必须"量"出来，不能"看"出来

总览那一轮的经验：三处"写了但从未生效"的样式（`:global()` 覆盖跨模块哈希类名、
JSX 没接上的 `.ovTrend`、被后一条规则覆盖掉的固定高度），源码评审、类型检查、
单测**全绿**，只有真实浏览器能把它们暴露出来。所以本计划的每一步都遵循：

```
真实 Electron + 真实解密库  →  量空白 / 裁切 / 错误  →  改  →  复量（同一脚本）  →  截图留证
```

### 1.2 度量口径

工具：`npm run ui:panel-audit`（`scripts/panel-audit.mjs`），逐页签执行：

| 指标 | 定义 | 判据 |
|---|---|---|
| 内容高 | 滚动容器内容总高（px） | 与"一屏 802px"对比看是否过长 |
| **最大空白带** | 把每一块**有内容的元素**（文字 / canvas / img / svg）投到内容坐标系的 1px 占用带上，连续未占用的最长一段 | 内容型面板应 < 150px |
| **空白占比** | 未占用行数 / 内容总高 | 内容型面板应 < 30% |
| 裁切 | `scrollHeight > clientHeight` 的可见子容器数量 | 必须为 0（列表要么滚，要么全显，不能切一半） |
| console error | 渲染层 error / pageerror | 必须为 0 |

**重要**：空白占比高**不等于**缺陷 —— 空状态（如「待办日程」的"暂无待办 + 怎么生成"）
是有意留白。判定时分三类：
1. **有意留白**（空状态、一次性 CTA）→ 只要信息完整就不动；
2. **加载态伪装成空白**（孤立一行"正在统计…"占满一屏）→ 必须改成有结构的加载态；
3. **真缺陷**（元素被拉伸、栅格空洞、内容没渲染出来）→ 重设计。

### R2 · 文件与存储 + 修好审计工具（已完成）

**起因**：审计说这个面板「0 项、空白带 651px、占比 88%」，看着像"数据没读到"。

**排查**（三步，每步都留了证据）：

1. **直接读库**：`hardlink/hardlink.db` 里 `image_hardlink_info_v4` 3309 行、
   `file_hardlink_info_v4` 864 行、`video_hardlink_info_v4` 132 行 —— 数据在。
2. **直调 Remote**：`getFiles {limit:1}` 返回 `total=4305, counts={image:3309,file:864,video:132}` —— 后端没坏。
3. **盯住面板 30 秒** + 受控复现：进入本页后 **前 3–6 秒头部显示「共 0 项 · 图片 0 / 视频 0 / 文件 0」**，
   然后才变成 4305。也就是说：`0` 是**加载期的谎报**，不是数据缺失。

**两个真问题（一个在界面，一个在工具）**：

| # | 问题 | 修法 |
|---|---|---|
| ① | 首屏取数期间页头写「共 0 项」、分类标签写「全部 (0) …」 | `loading && total === 0` 时页头改说「正在统计本机文件索引…」，标签去掉 `(0)`；只有真加载完且确实为空才显示空状态 |
| ② | **审计脚本把这种"首屏空面板"当成了落定**（文字稳定、无"加载中"字样），于是把一个加载态记成了布局缺陷 | 落定判定改为三条同时满足：文字连续 3 次不变 **且** 无加载措辞 **且** 无骨架元素，并且至少等 6 秒；每行结果附上正文开头，便于人眼复核 |

顺带做掉 U3/U6：
- 骨架的列宽与真实 `.fileGrid` 对齐（`ListSkeleton` 新增 `minCol`，这里传 200）——
  原来骨架按 120px 排 10 列、数据到了变 6 列，看起来像"布局跳了一下"；
- 空状态补上归因：文件索引来自本机解密库的 hardlink 记录，换过数据源要先去「设置 → 数据配置」完成解密。

**复量**：

| 指标 | 改前（被加载态骗了） | 改后 |
|---|---|---|
| 最大空白带 | 651px | **91px** |
| 面板文字量 | 100 字 | **1435 字** |
| 头部计数 | 共 0 项（前 3–6 秒） | 共 4305 项（加载中显示"正在统计"） |

**证据**：`.tmp-e2e/panels/文件与存储.png`；`files-loading.wiring.spec.ts`（5 条，含
"审计工具不许把加载态当落定"的元守卫，已做反证：去掉加载分支 / 削弱落定判定 / 去掉最短等待都会变红）。

**教训（写给后面的轮次）**：量错的工具比不量更危险。R2 有一半工作量花在**校准量具**上 ——
先证明"后端有数据、前端只是还没取到"，再决定改哪边。

### R3 · 资金往来：首次统计的加载态 + 复用总览快照（已完成）

**先量成本**（`getLedger` 直调）：冷 554ms、热 411ms —— 后端本身不慢。
真正的慢发生在**排队**：后端是同步 SQLite，本页查询会排在「总览」的全量统计
（`getOverviewInsights` 要扫 21 万条消息）后面，此时页面上只有一句
「正在统计资金账本…」+ 608px 空白，用户无法区分"在跑"还是"卡死"。

**两处改动**：

| # | 改动 | 效果 |
|---|---|---|
| ① | 加载态从一行字改为**有结构的一帧**：转圈 + `已用 Ns` 走秒 + 为什么可能偏慢（首次要解析全部消息 / 可能排在总览统计后面）+ 与真实布局同形的骨架（6 张指标卡 + 4 行表格） | 等待期间页面是"满"的，且有进度感 |
| ② | 首次进入时**先吃总览已算好的账本快照**（`dsh-wechat-overview-ledger-v1`，与本页字段完全同构） | 从总览点进来时立刻出金额（实测 280–290ms），后台再刷新 |

**验证方式（这轮换了个做法）**：本机后端 400–550ms 就返回，抢不到那个慢窗口
（试过替换 `window.electronAPI.wechat.call` 做延迟，但应用启动时已经取过桥面引用，换不掉）。
所以改用 **jsdom 确定性渲染**：把 `apiGetLedger` 挂成永不 resolve，面板就稳定停在那一帧，
再断言渲染内容。`ledger-loading.dom.spec.ts` 3 条：

1. 加载态有文案 + 走秒 + 耗时说明 + 骨架（>6 个占位条）+ 加载条容器；
2. 加载期间不出现任何金额（避免把 0 当真实数据）；
3. 本页无缓存但总览有时，立刻渲染总览那份（无加载态）。

**反证**：把加载态退回一行字 → 第 1 条变红；拿掉总览缓存兜底 → 第 3 条变红。两条都实测过。

**同时修正了对本面板的误判**：R2 审计里的「608px 空白」是加载态，等它跑完是 50px —— 所以 U2 的
重点从来不是布局，而是"等待期间有没有信息"。

### R4 · 总结：把"还差哪一步"讲清楚 + 微信问答复核（已完成）

**先说一个"不用改"的结论**：`微信问答`（U7）的落地态**已经完整** —— 标题、`269 个会话可检索`
的规模徽标、范围/时间筛选、居中空态（图标 + 一句话 + 三条能力芯片 + 三张示例问题卡 + "点卡片直接填入"提示）、
输入框、底部隐私说明。审计量到的 187px 空白是**空态的垂直居中**，属于有意留白。
计划里把它列为 P1 是基于空白率数字，看过截图后撤销 —— 记下来避免下一轮重复劳动。

顺带补了它唯一缺的一处：底部隐私说明原来只写"发送到所选模型"，**没说发给谁**。
现在会写明「`deepseek · deepseek-flash`」，未配置时直接提示需要先去「设置 → AI 大模型」。

**总结（U8）的问题**：全新用户（0 任务 0 记录）看到的是一张空卡 + 一句"还没有定时任务"，
下方 470px 空白；而**最关键的一件事一个字都没说** —— 总结是由模型生成的，没配模型点"生成"必然失败。

**改动**：

| 位置 | 改动 |
|---|---|
| 空态落地 | 新增两张并排卡：「三步拿到第一份总结」（① 配置模型 ② 手动生成一天 ③ 需要每天自动跑？）+「总结长什么样」（只读本机消息 / 五种格式 / 结果留档 / 可回溯） |
| 模型状态 | 读一次 `apiGetLlmConfig`：已配置显示 `provider · model` + 「查看」；**未配置显示"尚未配置 —— 总结由模型生成，没配模型无法产出" + 「去配置」** |
| 「去配置」 | 跳到「设置 → AI 大模型」节。这需要把 `openSettings` 一路传进来：`renderTab(...)` 新增形参 → `WechatDataPanel` 调用处传入 → `<DailySummaryPanel onOpenSettings={…} />` |
| 阅览页空态 | 补一个「去手动生成一份」出口，不再是一句"还没有历史总结"就结束 |
| 任务卡 | 让它吃掉剩余高度：空白落在卡片内居中，而不是堆在卡片下方 |

### R5 · 朋友圈：失败封面占位 + 校准审计的三条度量（已完成）

审计说这个面板「console error ×3 + 裁切 ×11」，是全站唯一带红的。查下去发现**两边各有一半问题**：

### R6 · 隐藏页签纳入审计 + 修掉读数污染源（已完成）

**目标**：导航里只渲染 17 个页签，另外 17 个 `hidden: true`（年度报告 / 周期报告 /
会话·公众号·服务号·客服 / 群聊监控 / 撤回消息 / 表情包 / 收藏表情统计 / 媒体资产 /
存储分析 / 公众号文章 / 转账红包 / 数据边界与出网 / 备份恢复 / 数据库健康 / 原图链路自检），
用户能从各面板的「详情 →」进入 —— 它们同样要量。

**驱动方式**：`WechatDataPanel` 只在**挂载时**读一次 `location.hash`，所以
写 hash → `reload()` → 等"导航按钮 **或** 设置弹窗"出现 → 量。
其中 4 个以设置弹窗打开（Radix 会把主内容区设成 `aria-hidden`，导航按钮查不到，
所以等待条件必须是"二者之一"），度量也改成**优先量弹窗本身**。

**然后踩了第六轮里最贵的一个坑**：第一遍跑出来 6 个隐藏页签是「651px 空白 + 只有一句统计中」，
看着像整片没渲染。抽查「表情包」单独重载 → **t=0 就有 1069 字数据**。
真因是**后端排队**：后端同步处理请求，前面几屏的重查询（存储分析 14.6 万项、朋友圈洞察、
年度报告…）把后面的请求全堵在队列里。

修法：每量一个隐藏页签前，先用一个**打到 worker** 的轻调用把队列等空
（`getSearchIndexStatus`；第一版用了 `listMethods` —— 它是主进程直接答的，
后端再堵也是 1ms，等于没等），并把排队耗时标在行尾。

**修正后的读数**（同一批页签）：

| 页签 | 修正前 | 修正后 |
|---|---|---|
| 表情包 | 651px | **85px**（自定义 30 · 表情包 0） |
| 存储分析 | 520px | **53px**（14.75 GB · 146,781 项） |
| 媒体资产 | 608px | **42px**（3,309 图 / 864 文件 / 132 视频） |
| 公众号文章 | 608px | **42px**（84 公众号 · 858 消息 · 857 文章） |
| 会话·公众号 | 84 字 | **33px**（完整会话列表） |
| 收藏表情统计 | 608px | **54px**（71 收藏 / 30 表情 / 24 文案） |

**仍然偏大的两个**（真实空态，不是渲染问题，留给 R7）：
`撤回消息 574px`（本数据集 0 条撤回 →「暂无撤回消息记录」）、`周期报告 515px`（未生成时的结果区）。
其余隐藏页签都在 15–184px 区间。**全站裁切仍为 0。**

**守卫**：`audit-instrument.wiring.spec.ts` 9 条，把六轮里踩过的口径一次性钉住
（落定三条件 / 加载措辞只在内容少时生效 / 排队探针必须打 worker / 裁切排除可滚与截断 /
资源失败与 JS 错误分流 / 隐藏页签的驱动与弹窗兼容 / 两个便捷开关）。
反证做了 **8 条**（换回 listMethods、去掉排队等待、破坏弹窗等待、删最短等待、
去掉三类裁切排除、去掉骨架检测…），逐条确认会红。

### R7 · 收口（已完成）

**① 两处真实的空态缺陷**

| 面板 | 改前 | 改后 | 做了什么 |
|---|---|---|---|
| 撤回消息 | 空白带 574px、两行字 | **422px**、304 字 | 把"为空"的**三类不同原因**分开写（没人撤回过 / 微信没保留缓存 / 解密库没同步），并给两个动作：刷新重读、去数据配置；再补一句"有数据时会看到什么" |
| 周期报告 | 空白带 515px、表单下方什么都没有 | **361px**、376 字 | 补"三步怎么做"（选区间 / 生成 / 复制）+「会得到什么」（区间统计、要点总结、**模型状态**、耗时口径），未配模型时给「去配置模型」 |

**② 页头口径（U12）**：`朋友圈`是**唯一**没有 `desc` 的面板，补上一句
「本机朋友圈动态 · 图片/视频/链接/评论互动，共 N 条；统计范围只含已解密的部分」。
由 `consistency-r7.wiring.spec.ts` 对**全部 30 个面板**断言"用 PanelHeader 就必须有 desc"。

**③ 年度报告：装不下时真的退回瀑布流**
海报模式的回退条件是 `@media (max-width:1200px), (max-height:779px)` —— 看的是**视口**高度
（本机 900，不触发），而被压缩的是**面板**高度（1440×900 下只剩约 700px）：海报照常启用，
**9 张卡片各自 `overflow:hidden` 把 20–30% 文字切掉**（「全年发出」128px 装 160px 的内容）。
改成按"**卡片是否真的被切**"判定（ResizeObserver + `data-compact`，复用同一套瀑布流规则，
并带上滞回避免抖动）。
复量：**年度报告 631px 全空 / 0 字 / 裁切 ×6 → 752px 内容、24px 空白、0 裁切、1615 字**。

**④ 顺带修掉最后一个读数污染源**：可见页签那一遍没有队列等待，于是同一份代码两次运行会给出
完全不同的数字（一次正常、一次满屏"统计中"）。现在两遍都先等队列排空；
隐藏页签那一遍还额外等到"面板确实有内容"再进入落定判定（重载后第一个隐藏页签曾被量成
"0 字 + 631px 全空"——壳渲染完了、页签内容还没 mount）。

**守卫**：`consistency-r7.wiring.spec.ts` 7 条，反证 6 条全红。
