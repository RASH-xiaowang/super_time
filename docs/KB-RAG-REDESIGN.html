Design Proposal · v1

知识库重设计：多库 · 文件解析 · RAG 检索

把「知识库」从「手写笔记的书架」扩成「你自己的文档底座」：多知识库并列，每个库可以容纳 条目（笔记）与文件（文档 / 表格 / 图片 / PDF），文件经解析、分块、向量化之后参与 **混合检索**（关键词 + 语义），让问答能引用你上传的东西，而不是只引用聊天记录。

范围：后端存储与检索 · @Remote 接口面 · 知识库面板三视图 · 上传与解析交互 · 权限与出网边界

两处注释里「许过愿的边界」，是本稿需求的原点

  • notes.ts 文件头：「本模块只读写本地库，不出网、不调用模型」。 这句话把「解析、嵌入」直接排除在 notes 模块之外 —— 于是本稿不新增 notes.ts 的任何函数，新能力全部落在新模块里。若图省事把解析塞进 notes，这句话就成了假话， 而它正是用户信任这个功能的依据。
  • embedding.ts 文件头第 3 条：「向量库位置：<数据根>/wechat_rag_vectors.db， 与稀疏索引同级，随数据目录一起迁移/删除」。它给的是**一条约定**（向量库是数据根下的 可重建产物）而不是一张表 —— 所以新向量库另开文件是顺着这条约定走，不是违背它。

3存储模型：两个新库、三张新表

分两个库不是洁癖：chunk 删了就没了，向量删了可以重建 —— 生命周期不同就不该同生共死。

3.1 wechat_kb_files.db

CREATE TABLE kb_files (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  kb_id         INTEGER NOT NULL,        -- 作用域。每条读写都必须带它（见 §12 变异测试）
  name          TEXT    NOT NULL,        -- 原始文件名，只作显示
  ext           TEXT    NOT NULL,        -- 小写扩展名，解析器分派依据
  size          INTEGER NOT NULL DEFAULT 0,
  sha256        TEXT    NOT NULL DEFAULT '',
  src_path      TEXT    NOT NULL,        -- 用户选的路径：只登记，永不写、永不删
  blob_path     TEXT    NOT NULL DEFAULT '',
  parse_state   TEXT    NOT NULL,        -- queued|parsing|chunking|embedding|ready|sparse_only|unsupported|failed
  parse_error   TEXT    NOT NULL DEFAULT '',
  parser        TEXT    NOT NULL DEFAULT '',   -- plain|html|mammoth|pdfjs|sheetjs|ocr(预留)
  page_count    INTEGER NOT NULL DEFAULT 0,
  chunk_count   INTEGER NOT NULL DEFAULT 0,
  char_count    INTEGER NOT NULL DEFAULT 0,
  include_in_rag INTEGER NOT NULL DEFAULT 1,   -- 0 = 只进本地稀疏索引，永不出网
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL
);
CREATE INDEX idx_kb_files_kb     ON kb_files(kb_id, updated_at DESC);
CREATE UNIQUE INDEX idx_kb_files_dedupe ON kb_files(kb_id, sha256);  -- 同库内按内容去重

CREATE TABLE kb_chunks (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  file_id    INTEGER NOT NULL,
  kb_id      INTEGER NOT NULL,   -- 冗余一列：检索时免 JOIN，把按库过滤下推到通道内
  ordinal    INTEGER NOT NULL,   -- 块序（0 基）
  text       TEXT    NOT NULL,
  char_count INTEGER NOT NULL,
  page       INTEGER NOT NULL DEFAULT 0,   -- PDF 页码；非分页文件为 0
  heading    TEXT    NOT NULL DEFAULT '',  -- 面包屑：md 标题栈 / 表格列名摘要
  created_at INTEGER NOT NULL
);
CREATE INDEX idx_kb_chunks_file ON kb_chunks(file_id, ordinal);
CREATE INDEX idx_kb_chunks_kb   ON kb_chunks(kb_id);

CREATE VIRTUAL TABLE kb_chunks_fts USING fts5(
  text, heading, content='kb_chunks', content_rowid='id', tokenize='unicode61'
);
-- 三个触发器（insert / delete / update）与 search.ts 既有 FTS 同款，不另立一套写法

为什么 kb_id 要冗余进 kb_chunks： 稠密检索必须能「先按库过滤、再算余弦」。若只存在 kb_files 上，每个查询都要 「先捞全库 chunk 再 JOIN 回文件表过滤」——这与消息侧 DenseSearchOptions.username 是同一个取舍：那里也是把过滤条件下推到通道内部。

3.2 wechat_kb_vectors.db

CREATE TABLE kb_vectors (
  chunk_id INTEGER PRIMARY KEY,   -- 直指 kb_chunks.id；不像消息侧要经 fts_rowid 绕一层
  kb_id    INTEGER NOT NULL,
  dim      INTEGER NOT NULL,
  vec      BLOB    NOT NULL,
  hash_lo  INTEGER NOT NULL,      -- 64 位 SimHash 签名，粗筛用
  hash_hi  INTEGER NOT NULL
);
CREATE INDEX idx_kb_vectors_kb ON kb_vectors(kb_id);
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
-- meta 记 schema_version / model / dim / built_at / rows —— 与既有向量库同款五键

三个设计选择，各给理由

  • 为什么 chunk 与 files 同库、向量单独一库。 分块文本是**解析产物**：删掉要用户重新解析（甚至要重新选文件）。向量是**可重建产物**： 换 embedding 模型、改维度，整个文件丢掉重建即可 —— 这正是既有向量库已在用的语义 （VECTOR_SCHEMA_VERSION 变化即自动重建）。两者生命周期不同，放同一个库里 会因为「重建向量」而连带冒「重建分块」的风险。
  • 为什么 chunk 与 files 必须同库同事务。 反过来说的同一件事：kb_files.parse_state='ready' 与 kb_chunks 里那 N 行必须一次事务落地，否则会出现「文件显示 ready、 点进去 0 个块」这种自相矛盾的状态 —— 而这种状态在界面上无法与「空文件」区分。
  • 为什么不做「一个文件属于多个库」。 库是作用域（作用域键只有 kb-scope-keys.ts 一个真源，见既有硬约定）。 多归属会让「切到这个库时我到底看到什么」不再可判定，也让删库时的归属决策组合爆炸 （移一半？移哪些？）。用户想两处都用，就上传两次 —— 同库内按 sha256 去重，跨库不拦（跨库本来就是两份归属）。

4解析流水线：状态机与崩溃恢复

八态状态机，三条失败支路各走各的，不许「静默跳过」。

4.1 六条硬规矩

  • 解析只发生在后端进程。 渲染进程没有 fs；wechat:call 只传路径不传字节 —— 这是 main.js:840 已经立下的约定（「视频有几十 MB，不适合经 IPC 传字节」）， 本稿沿用并把上限收紧到「连小文件也不传字节」，理由是不想让「传不传得动」取决于文件大小。
  • 解析必须让出事件循环。 后端是独立进程，解析大 PDF 会占满它的事件循环， 连带所有 @Remote 调用一起卡住。既有工具 yieldToLoop()（从 query/search.ts 导出）已在用，本稿规定：每抽一页 / 每 200 块让出一次。
  • 进度走事件，不走轮询。 渲染层带一个自己生成的 jobId， 进度由后端通过 wechat-kb/progress 事件推出去，取消走 cancelKbJob({ jobId }) 唤醒对应 AbortController —— 与 gateway.ts:161-182 的 StreamJob 完全同款。那里注释写明了 为什么不能把 onProgress / AbortSignal 当 RPC 参数传： 回调是函数、signal 是宿主对象，序列化时会被丢掉。
  • 崩溃后只重置一次，不是每次读列表时判断。 进程启动时把 parsing | chunking | embedding 一律改回 queued（这三个状态 物理上不可续跑）。若改成「读列表时看到 parsing 就当作 queued」，则一个正在正常解析的 文件会被列表读操作误判 —— 那是把一个启动期修复变成了并发 bug。
  • 不支持的类型在选择时就挡，不在解析时才说。 对话框按白名单过滤扩展名， 用户看不到 .zip / .mp4。unsupported 只留给「扩展名在白名单里、但这台机器上 没有对应解析器」的情况（例如没装 pdfjs 时的 .pdf）—— 文案要写成 「这台机器上的解析器不支持 PDF」，而不是「文件损坏」。
  • 解析的输入永远是 blob 副本，不是 src_path。 这一条决定了「用户把文件挪到别的文件夹」不会弄坏知识库。src_path 只用于两件事： 「在文件夹中显示」、以及重试时提示用户原文件是否还在。

为什么图片本期只登记，而不是先接一个 OCR

三条理由叠加：① OCR 要中文模型，体积与首启时间都是可见代价；② 纯 JS 的中文 OCR 识别率 不足以支撑「检索命中后把它当证据给模型」这件事 —— 给模型错的证据比不给更糟； ③ 用户真正的「文件知识」绝大多数在文档里，先做文档的收益/成本比高得多。 但界面上必须说清楚：图片行的状态写「已登记，未识别内容」，并明确 「当前只能按文件名搜到它」。留了 parser='ocr' 的位置，将来插入不用改表。

5分块策略：字符口径与表格例外

分块决定了「检索命中的东西有多像一段人话」。这一节的每个数字都有理由。

目标块长
500 字符 · 重叠 80 字符
中文技术文档约 250~350 字一个自然段；500 字能容纳「一段 + 它的列表」，重叠 80 字保证跨块边界的句子仍能被完整召回。
切点优先级
段落 > 句子 > 硬切
依次尝试 \n\n、。！？；\n，都没有才按 maxChars 硬切。硬切时 heading 追加「续 N」——让模型知道这是残段。

5.1 表格类文件不能按字符切

一个 CSV 的两行：
姓名,部门,入职日期,月薪
张三,研发部,2024-03-11,28000

按 500 字符硬切的后果（块边界正好落在一行中间）：
… 张三,研发部,2024-03-11,28       ← 块 A 结尾：半条记录
000 李四,市场部,2023-07-02,26000    ← 块 B 开头：另外半条 + 一条完整记录

本稿的做法 —— 按行组分块，每块首行永远是表头：
┌ 块 0 ─ heading: 列名 姓名|部门|入职日期|月薪 ─ 行 1-40
│   姓名,部门,入职日期,月薪        ← 表头行，每块都带
│   张三,研发部,2024-03-11,28000
│   …（至第 40 条记录）
└ 块 1 ─ 同 heading ─ 行 41-80（表头行再带一次）

为什么块首必须重复表头。 检索命中的是一个块、送给模型的也是那个块。 块里没有列名，「28000」这个数字对模型就没有含义 —— 它无法回答「谁的月薪是 28000」。 多存 40 行表头的代价，与「证据可读」的收益相比可以忽略。

为什么是 40 行。 取「行宽 × 40 ≈ 500 字符」的量级：常见表格一行 10~15 个字段、约 60~120 字符，40 行落在 2400~4800 字符区间。这个数字最终要由 kb-chunk.spec.ts 的实测断言钉住，而不是保留成可调参数 —— 它属于 固化的产品默认（与检索参数同一条纪律）。

5.2 其余分支

输入形态行为理由
空文件 / 只有空白ready，chunk_count=0，行上显示「无可用正文」这不是失败。`failed` 要留给「抽取器抛错」，否则用户会去排查一个不存在的问题
超长单行（一行 50 万字，常见于压缩 js / 单行 json）按 maxChars 硬切，heading 记「续 N」不切则一个块塞爆上下文预算，整份文件等于不可检索
同一文件解析出 > 20000 块硬截断到 20000 块，parse_error 写明「已截断至 20000 块」两个保护合一：不让一次上传把出网闸门变成批量外泄；也保护向量库体积
Markdown 标题维护标题栈，每个块 heading 记 H1 › H2 › H3给模型的面包屑，也让 UI 能显示「命中哪一节」（比页码更精确）
无标题的纯文本heading 取文件内首个非空短行（≤ 40 字）聊胜于无：通常是个文件的题名

为什么用「字符」而不是「token」

全项目的上下文预算口径都是字符（config.ts 的 compress.maxChars=6000、excerptOf(body, limit=140)）。 引入 tokenizer 意味着新增一个依赖 + 与远端模型的分词器版本绑死，而收益只是 「块长更精确」。本稿选择与既有口径一致：字符就是预算单位， 偏差由嵌入接口自己的截断行为兜住。

6检索与相关性排序

链路一行不改地复用，换的是语料与策略表 —— 以及「压缩」这一步要重写。

阶段既有实现本稿处置为什么
意图路由 intent.ts，6 类意图（recency_lookup / entity_lookup / time_range / aggregation / comparison / open_qa）+ defaultPolicyFor() 新增 kb_default 策略 recency_lookup（按时间取最新）与 time_range 对文件语料无意义 —— 文件没有消息时间轴。entity_lookup / aggregation 仍然成立，保留

稀疏召回 search.ts 的 FTS5 + BM25 换表：kb_chunks_fts，查询加 WHERE kb_id=? BM25 对中文短块仍是最稳的词法通道
稠密召回 embedding.ts：EmbedFn 注入 + SimHash 粗筛 + 精确余弦 + minSimilarity 换表：kb_vectors；沿用同一个粗筛实现 只有语料换了。SimHash 粗筛的逻辑与文档集无关

时间通道 time（按日期段直取消息，唯一不做内容匹配的通道） 关闭 知识库里没有「某天聊了什么」这种问题。文件的时间只是元数据 → 归 structured
融合 fusion.ts RRF（k=60，只用名次不用原始分） 原样复用 RRF 只吃名次，天然免疫「稀疏分与余弦分量纲不同」
重排 rank.ts 7 特征线性组合（sparse / dense / entity / coverage / timePref / recency / agreement） 换权重：kb_default 下 recency=0、timePref=0，抬 coverage 与 agreement 文件语料里「新旧」不该加分；但「两个通道都召回」与「查询词覆盖率」在文档上更可信

  score

6.2 结果区要不要给权重旋钮？——不给

既有产品要求是检索参数全部固化、界面不暴露（「检索设置（RAG）」面板已于 2026-09-17 从界面移除，RetrievalPanel.tsx 已删除，参数由 defaultRetrievalConfig() 提供、界面不出现任何入口）。 知识库检索没有理由开这个口子 —— 目标用户不熟这些参数。

但「不给旋钮」不等于「不给解释」。UI 要给的是可解释性： 这条结果被哪些通道召回、各排第几、命中了哪些词。这两件事的区别是： 前者把决策权交给用户，后者把决策过程讲给用户听。

6.3 降级必须被看见

触发期望行为为什么
该库还没建向量索引 稀疏通道正常工作，结果区标题标「仅关键词（未建向量索引）」，旁边一个「建立索引」按钮 「搜不到」与「索引没建」在界面上必须能分开 —— 否则用户会以为知识库里没有这个内容

库内没有任何 chunk 返回空结果 + dense.note='库内无分块'，界面按「空库」文案呈现 与 N1 同一条纪律：空结果的原因要能说出来

一个真实的边界：reassign 到目标库时，若目标库已有同 sha256 的文件， 唯一索引不允许两行 → 该文件不迁移，计入 removedFiles， 回执文案写「N 个文件与目标库内容重复，未迁移」。

9权限与访问控制

先说清没有的，再落四条真实存在的边界。

本机没有的东西，不能假装有

这是一台机器上的单用户桌面应用：没有账号体系、没有身份主体、没有共享。所以 「基于角色的访问控制（RBAC）」「成员权限」「分享链接的可见范围」在这里没有落点 —— 做出来就是装饰。本稿把「权限」重新解释为下面四条能被代码断言的边界。

9.1 四条真实边界

#边界落点怎么被守住
1 库级：默认库不可删（可改名）；删非空库必须显式选 purge / reassign notes.ts:444（DEFAULT_KB_ID 拦截）、KbDeleteAction 必填不给缺省 既有：类型系统 + delete-kb-cascade.spec.ts（本稿扩文件部分）
2 出网闸门：嵌入 = 新增出网点，必须过 privacyGate('kb_embed', …) gateway.ts:455 privacyGate；被拦时整体降级为纯稀疏 tests/privacy-statement.spec.ts 会自动要求 kb_embed 出现在 docs/PRIVACY.md §四出网点清单里
3 文件级出网开关：include_in_rag=0 的文件只进本地 FTS，永不送嵌入接口 新列 kb_files.include_in_rag；buildKbVectorIndex 跳过这些文件 kb-vectors.spec.ts：断言 include_in_rag=0 的文件不出现在 kb_vectors 里
4 来源保护：src_path 只登记，永不写、永不删、永不移 删除路径只清登记 / chunks / FTS / 向量 / blob 探针第 9 条：删文件后断言 fs.existsSync(src_path) 仍为真
5 副本隔离：新建的两个库 不进 BOOTSTRAP_ITEMS dirs.ts:46 常量表（与 wechat_notes.db 现状一致） 源码级：断言两个新库名不在该常量表里

9.2 敏感文件：为什么「打码」不是正确答案

既有能力里有一个「敏感字段打码」（手机号 / 身份证号在出站前被替换）。 直觉上应该对所有出网文本一律打码，但用于嵌入时会出现一个反效果： 打码会改变文本，向量因此失真，召回率下降 —— 而且用户看不出来 （他只看到「搜不到」）。

所以本稿的答案是第三条路：对含敏感内容的文件用「文件级出网开关」， 而不是靠打码。勾掉之后该文件完全不出网，但仍然可被关键词搜到 —— 这正是「库里有合同，但我还想搜到它」的真实需求。界面上这个勾选框旁边必须写明这条代价， 而不是藏进设置页。

9.3 出网点清单必须同步（会转红，是好事）

privacy-statement.spec.ts 用正则从 gateway.ts 里抽出所有 privacyGate('…') 的功能名，逐个断言它出现在隐私声明里 —— 也就是 新增出网点而漏写文档 → 用例转红。本稿新增 kb_embed， 因此实施时必然要动 docs/PRIVACY.md §四的清单表。这不是可选项，是一条被守卫的 一致性契约。

  • 功能名用 kb_embed 而不是复用 ask_embed：审计日志里要能分清 「问答检索的向量化」与「知识库文件的向量化」——二者的量级与触发时机完全不同。
  • 全局开关仍是同一道：数据配置 → 数据边界与出网 → 禁止 AI 出网 一起拦下。
  • 被拦下时不进审计日志（与既有约定一致：只有被放行的调用才记录）。

10边界与失败模式

每条写成「触发 → 期望行为」，落地时能直接变成用例。

#触发期望行为为什么这么选
1选了白名单外的类型（.zip / .mp4 / .pages）对话框白名单直接不显示；若绕过（拖拽 / 直接调 RPC）→ rejected + 原因「不支持的类型」不给用户「传进去才发现不行」的体验
2选了 .pdf 但本机没装解析器unsupported + 「这台机器上的解析器不支持 PDF」，不是「文件损坏」两种原因的排查方向完全不同
3原文件被用户改名 / 移动 / 删除知识库完全不受影响（解析源是 blob 副本）；「在文件夹中显示」失败时给一句说明文件被移动是常态，不该让知识库跟着坏
4解析中途进程被杀 / 崩溃下次启动把 parsing|chunking|embedding 全部重置 queued 并重新排队三个中间态物理上不可续跑；不重置会永久转圈
5嵌入接口不可用（无 Key / 断网 / 被闸门拦）文件落 sparse_only + 原因；searchKb 仍可用（纯稀疏）不能整块失败 —— 那会把已经解析好的正文一起废掉
6同一文件在同一库重复上传唯一索引拦下 → rejected「该文件已在当前库中（按内容判定）」按内容（sha256）而不是按文件名判定：改名重传不该产生两份
7删库选 reassign，但目标库已有同内容文件该文件不迁移，计入 removedFiles；回执写「N 个文件与目标库内容重复，未迁移」唯一索引不允许两行同 sha256；静默合并会让用户以为文件丢了
8换了嵌入模型 / 维度变了状态 ready=false，界面提示「向量索引需要重建」+ 一个按钮沿用既有 VECTOR_SCHEMA_VERSION 的语义，不自动静默重建（出网量会突增）
9库内没有任何 chunk 时检索空结果 + dense.note='库内无分块'，按「空库」文案呈现空结果的原因要能说出来（N1 纪律）
10分块参数改动后已有 chunk 不自动重算；界面上给每行的「重新解析」一次参数变更触发全库重嵌的代价是突发的出网量与耗时；幂等性优先
11一个 5000 页 PDF 解析出 8 万块硬截断到 20000 块，parse_error 写明「已截断至 20000 块」防「一次上传把出网闸门变成批量外泄」，也护向量库体积
12列表有 5000 个文件分页（limit），不做虚拟滚动与项目其它列表（DataTable）保持一致，不为此引入新机制
13库列表读失败（readError）给「重试」，不给「新建」既有纪律：空列表会被读成「一个库都没有」而诱导用户新建，用一个新空库盖住真问题

11落地分步（切口）

六步，每步都能独立验证、独立回退。不写时间估计，写切口。

步骤 1  分块器 + A / A' 档解析器                    纯函数，零新依赖，纯单测
         └ 可独立验证：kb-chunk.spec.ts 全绿
         └ 可独立回退：不碰 db、不碰界面、不碰 RPC —— 删文件即可
         └ 产出：分块是「一段可被人读的话」，而不是切字符串

步骤 2  wechat_kb_files.db + 登记 / 列表 / 删除 + 文件视图
         └ 此时不做嵌入：这一步结束就有「文件书架」
         └ 补 dialog:open-file 的 SUPERTIME_OPEN_PATHS 钩子（§7）
         └ 可独立验证：真机探针能上传、能看到状态、能删（原文件仍在）

步骤 3  FTS5 稀疏检索 searchKb（只开 sparse 通道）        第一个检索闭环
         └ 可独立验证：探针输入夹具里的独有短语，命中该文件
         └ 这一步之后即使永远不做向量，「文件可被搜到」已经成立

步骤 4  wechat_kb_vectors.db + buildKbVectorIndex + 稠密通道 + kb_embed 隐私登记
         └ 含 docs/PRIVACY.md 清单同步（否则 privacy-statement.spec.ts 转红）
         └ 可独立验证：kb-vectors.spec.ts + 探针断言降级路径（关掉出网 → 仍能搜到）

步骤 5  B 档解析器逐个接（pdfjs → mammoth → SheetJS）    每个一格独立提交
         └ 某个依赖出问题（体积 / 打包 / 装不上）不影响前四步的任何能力

步骤 6  体验层：排序 / 空态文案 / 降级标注 / 响应式断点 / 抽屉动效
         └ 为什么放最后：前五步任何一步的失败都会改变「有多少东西可展示」，
           先做视觉必然返工

唯一的顺序依赖

步骤 2 依赖步骤 1（没有分块器就没有 chunk_count），步骤 3 / 4 依赖步骤 2。 步骤 5 与步骤 3 / 4 互不依赖 —— 纯文本族已经能跑通全部检索能力， PDF / docx / xlsx 只是让更多文件「能进得来」。这个性质让整个交付可以中途停在任何一步 而不留残骸。

13明确不做，以及为什么

这节最省未来的时间：把「看起来合理但会伤到别处」的选项当场否决掉，下次不必重开一遍。

不做理由
一个文件属于多个库 库是作用域，多归属让「切到这个库看到什么」不可判定；也让删库时的归属决策无法穷尽（移一半？移哪些？）。想两处都用就传两次
跨库检索 / 跨库文件引用 同上。而且 [[链接]] 的解析域已经按库（notes.ts 的标题唯一在库内）—— 文件再开一条跨库通道，两种作用域语义会互相打架
在应用里编辑文件正文 登记的是「你电脑上的那个文件」。改正文要么改原文件（我们不碰），要么产生第二真相 —— 而第二真相会在下次重新解析时被冲掉
图片 OCR / 音视频转写 中文 OCR 的识别率不足以把结果当证据送给模型（给错证据比不给更糟）；音视频需要大体积依赖。表里已留 parser='ocr' 的位置，将来插入不用改结构
自动监听文件夹（watch） 不可见的盘点：用户不知道哪些文件被读了、被出网了。上传必须是主动动作
多用户 / RBAC / 分享链接 本机单用户桌面应用，没有身份主体。做出来是装饰，还会给人「有权限控制」的错觉
云端同步知识库 与「本地优先、出网可控」的产品边界冲突 —— 一次云同步会把出网量从「可控的嵌入」放大成「整库上传」
暴露检索参数（权重 / topK / 阈值） 沿用既有产品要求：检索参数全部固化，界面不出现入口。给解释，不给旋钮
删除 / 移动用户的原文件 src_path 只登记。删除只清我们的登记、chunk、向量与 blob 副本 —— 确认文案里要写明这一点
把 chunk 向量塞进既有的 wechat_rag_vectors.db 那张表的 PK 是 fts_rowid、列里有 username / local_id / create_time，是给消息量身定做的。混用会污染 rows 与 ready 的判定，一步把一个冷路径改成了热路径
分块参数变更后自动重算全库 一次参数变更触发全库重嵌 = 出网量与耗时的突发。改成逐文件显式「重新解析」
虚拟滚动 用 limit 分页即可，与项目其它列表一致。不为一个页面引入新机制
在「文件」之外再加侧栏入口 侧栏入口数保持 17，新视图作为知识库的第三段（hidden: true 但可路由）。它和笔记、图谱是同一主题的三种看法，不该在侧栏各占一格
