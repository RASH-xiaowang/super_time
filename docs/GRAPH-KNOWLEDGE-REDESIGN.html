知识图谱重设计：借鉴「社交图谱」的设计理念

0现状盘点：原有知识图谱是什么

先钉住事实，再说改什么 —— 下面每条都能在代码里指到出处。

它已经有的（不用重建）

  • 与社交图谱同构的画布：GraphCanvas 按 variant 二选一，力导向（FA2 + Worker）、悬停高亮、点选详情、拖拽、滚轮缩放、适应视图、深度过滤、固定节点、搜索定位、圈子聚焦、SVG/PNG 导出 —— 全部已经共用。
  • 同构的数据契约：buildKnowledgeNetwork 产出的就是 BuiltGraph，画布无需区分数据来源。
  • 缺口显性化：stub 节点（虚线描边 + 半透明）已经能把「被引用却没写」暴露出来，点它就地成文。

它缺的（这才是要重设计的理由）

七个真实缺口

  1. 只有一种关系。 标签（notes.tags）是一等字段，却完全没进图。所以它画的是「引用网络」，不是「知识网络」——两篇同标签、明显同主题的笔记彼此毫无关系。
  2. 没有强度。 边权只改边长，不改线宽、不进社区检测权重，也没有「枢纽」概念。看不出哪条关系更重要。
  3. 没有层次。 所有节点同一平面。半径按连接度算，但没有结构性角色（主干 / 叶子 / 孤岛），读不出知识结构是树状还是网状。
  4. 社区检测在稀疏图上失效。 笔记库普遍存在大量零连接笔记（summary.orphanCount），加上 <3 → -1 的阈值，圈子数常年为 0 —— 用户看到的是「圈子的功能坏了」。
  5. 孤岛被「排除」而不是被「接纳」。 它们被排到主簇下方的网格带里（复用 isolatedStripPositions），虽然可见可点，但没有任何回到网络的路径。
  6. 缺口没有量化排序。 refCount 就在数据里，但界面没有给出「最该先补哪 5 篇」。
  7. 没有可执行的整理动作。 由图到行动只有三条缝：点开编辑、点 stub 建笔记、删除。没有「补一条链接」这件事。

1借鉴社交图谱的哪些核心特征

不是抄观感，是抄这六条已经付出过代价的机制。

社交图谱的特征它在社交侧的原始形态知识图谱的对应物
① 枢纽引力
原样迁移		 「我」是全图唯一锚点：intimacyPull 让消息量越高离中心越近（dist = 340 − t×260，strength = 0.02 + t×0.16）。 锚点换成「当前焦点笔记」（选中的那篇，默认取最近编辑的一篇）。[[链接]] 距离设为 150/√w，与锚点越相关的笔记被拉得越近 —— 图自动围绕「我正在写的东西」展开。
② 连接强度 → 距离 + 线宽
原样迁移		 消息量 → 亲密度 → 边长 / 线宽 / 弹簧松紧；布局前先做 layoutWeight() 的 log 压缩（把 1~数千压到 1~4），否则枢纽边会把所有人吸成一条线。 强度来自两处：[[链接]] 的共现次数与两篇笔记的共同标签数。共用同一套 log 压缩与 dist 公式 —— 这是「强度」在图上有三层表达（距离、线宽、拉紧程度）的完整形态。
③ 观测层 / 推断层分额度
核心迁移		 「真实观测到的关系」（亲密度 / 共同群）有多少画多少；「推断出来的关系」（同备注编号 / 首字相同）必须先用 edgeHeadroom() 问「还剩几条」再生长，且固定画虚线。血泪证据：混在一起夹额度时，推断层会把 245 条真实观测边挤掉。 这是最值得抄的一条。 知识侧：观测层 = [[链接]] + 共同标签；推断层 = 标题同前缀。推断层永远不挤观测层，且推断边必须是虚线 + 带一个「接受」动作。
④ 社区结构 → 主题簇
原样迁移		 加权 Louvain（detectCommunities），圈子决定颜色；communitySeparation 让圈与圈之间留白；侧栏「圈子概览」按成员数列出，支持点击聚焦、悬停预览。 同一个函数，换个输入：跑在 wiki + 共标签 上（原实现只喂稀疏的 wiki，所以出不来圈子）。圈的语义更可读 —— 它就是「主题簇」，概览里显示簇内高频标签而非人名。
⑤ 重要性 → 半径
原样迁移		 radiusByIntimacy：指数饱和曲线（1 − e^(−w/200)），区间 5–34，保证「消息量差异肉眼可辨」。 同一条饱和手感的 radiusBySqrt，输入换成加权连接度（反链权重高于出链 —— 被引用比引用别人更「中心」）。区间保持 16–46：这一档是实测定过的，太小会被画布的 8px 下限压平，链接数不同的笔记会长得一样大。
⑥ 孤岛单独安置
迁移 + 强化		 isolatedStripPositions：度 0 的节点不参与力导向，按确定性网格排在主簇下方，位置只由半径 + nodeGap 决定 —— 调力度滑杆不会让它们乱跑，包围盒也不会被散点撑大。 升级为「收件箱区」：孤岛不是废料，是待整理队列。网格区旁给「建议关联 Top 3」（从推断候选里取分数最高三条），一键接回网络。
⑦ 额度单一真源
工程纪律		 额度只在 graph-budget.ts，建模层与绘制层都必须 import；任一侧自写整数就退化成「模型里有边、图上没画」——这个缺陷被真机审计量化过两次。 新增的共标签层是 O(标签大小²) 增长（一个热门标签挂 100 篇 → 4950 对候选），必须走同一套 edgeBudget / edgeHeadroom。这是抄纪律，不是抄观感。

为什么「共同标签」不建标签节点

一个自然的想法是把标签也画成节点（笔记 ↔ 标签二分图）。这里明确不采用，理由三条：

  • 会破坏半径语义。 标签节点的度远大于任何笔记（一个标签挂几十篇），力导向会把同标签笔记拉成一个以标签为中心的星形——「半径 = 笔记重要性」立刻失效，笔记全变叶子。
  • 与社交图谱不同构。 社交图谱里人—群之间也没有画边：共同群是人与人之间的边。照这个口径，共同标签就该是笔记与笔记之间的边。同构才能复用额度、社区检测、圈子概览这一整套。
  • 入口本来就存在。 「点标签看全部同标签笔记」是笔记库（KnowledgeBase）列表视图的职责，图谱不必再给一次。两种视图分工：「图谱看结构，列表看清单」。

2目标用途

从「我写了什么」变成「我的知识长什么样、下一步该写什么」。

用途 1 · 找缺口
最该补的 5 篇
按 stub 的 refCount 降序 —— 被引用最多、却还不存在的概念排最前，一键成文。
用途 2 · 找孤立
收件箱 + 建议关联
零连接笔记不再只是「被排到下面」，而是带「建议关联 Top 3」的待办队列。
用途 3 · 找主干
枢纽 / 叶子一眼可辨
枢纽加外环（这是「目录页」），叶子细描边。能看出结构是树状还是网状。
用途 4 · 找路径
两篇之间隔着什么
选 A + 点 B → 高亮最短路径。回答「这两个概念是怎么连上的」。

一句话定位

原有知识图谱是「引用的可视化」——好看，但看完不知道该做什么。
重设计后是「知识组织的驾驶舱」——每一处视觉差异都对应一个可执行动作： 虚线 → 可以接受成链接；收缩的网格区 → 可以接回网络；枢纽外环 → 可以当目录继续扩写。

红线：图与社交数据彻底解耦

关系：从 1 层扩到 3 层

层kind语义方向强度来源额度口径

刻意不做的第 4 层：「正文共现专名」

最诱人的一条推断是「两篇笔记正文里都频繁出现同一个专名，但没有 [[链接]]」。 不做，因为中文专名识别没有可靠且零依赖的实现——项目里没有分词器，任何近似方案都会 在真机上产生大量假边，而假边恰好会吃掉真实观测边的额度（社交侧已经量化过这个后果）。 推断层只用确定性、零依赖的标题前缀规则，与社交侧的 remarkClass （备注前缀 + 编号，如「宜州一中404」）是同一个手法。这条纪律 = 「可复现、可断言」。

4层级与关联规则

「层级」有两个含义，必须分开：一个是角色（不改变拓扑），一个是边的优先级（决定拓扑）。

4.1 结构性层级：四个派生角色

由度数算出，是纯函数（建议落在新文件 graph-role.ts），不引入新数据、不改变边表。

4.2 关联规则：优先级 → 去重 → 额度

  1. 优先级由插入顺序决定：wiki > tag > prefix。高优先级已经占掉的点对，低优先级不再生成。这是社交侧「共同群 > 同备注编号 > 首字」同一套语义。
  2. 去重唯一写入口：所有推断边都走 addInferred(a, b, kind)，共用同一个 paired: Set。点对无向化（a < b 字典序作 key）。同一对笔记只能有一条边——社交侧血泪：重复边会让详情面板 React key 相撞、度数统计虚高。
  3. 额度不新写整数：直接 import graph-budget.ts。观测层夹 min(OBSERVED_EDGE_CAP, edgeDensityCap(n))；推断层只问 edgeHeadroom(n, used)，其中 used 必须是已产出的边数（不是原始候选数）。
  4. 不变量：模型边总数 ≤ edgeDensityCap(n) ⇒ 模型里的边一条都不会被绘制层裁掉。这条是「模型有边、图上没画」这类缺陷的根治方案。

4.3 社区检测的输入与阈值（两处必须改）

项原实现重设计后理由
喂哪些边 只有 wiki wiki + tag（观测层） 稀疏的 wiki 上 Louvain 出不来圈子 —— 这是「圈子数常为 0」的主因
prefix 边 — 不喂 与社交侧「首字层刻意不参与社区检测」同一理由：启发式规则不该改圈子归属，蓝虚线跨圈子穿过反而正好说明「这是推断」
stub 不参与（-1 中性灰） 不参与（保持） 「尚未存在的笔记」被分进圈子会产生误导
小组阈值 成员数 < 3 → -1 成员数 < 2 → -1 笔记库量级是「几十到几百」，2 篇同主题是完全正常的簇；社交侧用 3 是因为通讯录有几百人、2 人组多半是噪声

4.4 截断顺序 = 价值顺序（修正一处现状）

现状是 noteNodes.slice(0, limit)，而 noteNodes 的顺序来自后端的 ORDER BY updated_at DESC —— 实际效果是「最近更新优先」。 这与「半径 = 连接度」表达的价值观不一致。改为：按连接度降序截断 （主干优先保留），并且孤岛优先被移出主图、进收件箱区——它们本来就不该占主图的额度。 stub 继续不参与截断（数量少，截掉就失去「缺口提示」的意义）。

7关键设计要点

  1. 同构优先，不平行造第二套。节点种类写下时是 2 类（2026-09-19 文档实体层后为 4 类， 且新两类仍在知识库之内）；边的语义层从 1 层扩到 3 层；画布 / 布局 / 额度 / 社区检测全部复用。 任何「知识图谱专用的第三套逻辑」都是信号：应该先问它能不能表达成社交侧已有机制的换参。
  2. 观测层与推断层必须分额度。共标签是观测（用户亲手打的），标题前缀是推断。推断层永远只在余量里生长，且固定画虚线。社交侧的量化证据：混夹会让 245 条真实边消失。
  3. 额度只有一个真源。 复用 graph-budget.ts，知识侧不新写任何整数。共标签候选是 O(k²)，必须先问 edgeHeadroom()。
  4. 去重只有一个写入口。 addInferred(a, b, kind) + 共享 paired: Set，优先级由插入顺序决定。
  5. 社区检测只吃观测层（wiki + tag）；prefix 与 stub 不参与；小组阈值 <3 → <2。
  6. 孤岛不是废料。 度 0 的笔记移入收件箱区（复用 isolatedStripPositions：不参与力导向、不受力度滑杆影响、不撑大包围盒），并配「建议关联 Top 3」。
  7. 每一处视觉差异都要对应一个可执行动作。 虚线 → 可接受成链接；收件箱 → 可接回网络；枢纽环 → 可当目录扩写。只画不给动作的推断层是负资产。
  8. 全部派生规则必须是纯函数 + 显式 tie-break。 前缀 key、角色判定、候选排序都用 localeCompare 等确定性比较；初值坐标继续用 id 哈希（initialPosition），绝不引入 Math.random——否则「同一张图每次打开都长不一样」，也没法写成回归用例。
  9. 截断顺序 = 价值顺序。 按连接度降序保留主干；孤岛优先移出主图。stub 不参与截断。
  10. 不碰产品红线。 节点只来自知识库；buildKnowledgeNetwork 签名继续不接受社交快照；「融合视图」不复活。

8与原有知识图谱的主要差异

维度原有知识图谱重设计后
关系类型 1 种（[[链接]]） 3 层：wiki 实线+箭头 / tag 细实线 / prefix 金虚线，按观测/推断分额度
标签 完全不进图（tags 字段被浪费） 作为派生边（共同标签数 = 强度）——刻意不建标签节点，保住半径语义与同构性
强度 权重只影响边长 影响边长 + 线宽 + 布局的 log 压缩，并且是社区检测的权重
圈子 / 社区 只喂稀疏 wiki + 阈值 <3 → communityCount 常为 0，侧栏「圈子概览」基本是空的 吃 wiki + tag 双来源，规模足够；阈值下调到 <2；圈的语义明确为主题簇
层次 无 —— 所有节点同一平面 4 个派生角色（枢纽 / 普通 / 叶子 / 孤岛）+ 角色筛选；枢纽加外环
孤岛处置 排到主簇下方网格带（可见但被「排除」） 升级为收件箱区 + 建议关联 Top 3，可一键接回网络
推断层 无 标题同前缀（锚点生成树 + 余量回填，金虚线），并配「接受并写回」按钮
可执行性 只能看 · 点开编辑 · 点 stub 建笔记 新增「补链建议」一键写回 [[链接]] · 「收件箱」建议关联 · 两点最短路径
时间维度 无 近 7 天更新的笔记加柔光晕（外观层，不改拓扑，默认开可关）
额度纪律 无（wiki 边天然稀疏，从未触发） 新增层同样夹 edgeBudget / edgeHeadroom，与社交侧同源
截断口径 noteNodes.slice(0, limit)，实际按 updated_at 顺序 按连接度降序（主干优先），孤岛优先移出主图
代码结构 buildKnowledgeNetwork 一个函数直出节点与边 边层在 graph-model.ts 内按层构建（唯一写入口 addInferred）+ 新增 graph-role.ts 角色层；画布 / 布局 / 额度全部零改动

9落地切口（分四步，每步独立可验收）

步骤做什么验收口径
P0 先把骨架换成「分层 + 额度 + 唯一写入口」
此时只有 wiki 一层，行为不变，但推断层的地基就位		 现有知识相关 spec 全绿；断言「模型边数 ≤ edgeDensityCap(n)」；typecheck ×2 + build:ui（含 vite build）
P1 共标签层
加 kind:'tag'，观测额度内生成；社区阈值 <3 → <2；图例与侧栏文案		 真机（几十~几百篇笔记）communityCount > 0，且 wiki 边一条不少（与 P0 逐一比对）

每步都必须跑的验收

  • typecheck（客户端 + 后端两条） · ui:smoke · check:wx-tokens · docs:api:check

  • 图谱改动必须跑真实数据验收（working/*.audit.spec.ts）：夹具测不出的规模问题只有真数据能暴露。⚠ 注意 buildGraph 返回值已截断，判断「某一层是否被切光」必须用同一份节点数据复算原始规模。
  • 真机截图核对：图谱要判.stage 里的 canvas 且 .rail 同时存在（不能用「有没有 canvas」判定，ECharts 面板也有 canvas）。
