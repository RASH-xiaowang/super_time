## 一、性能：范围 / 目标 / 验证

### 1.1 范围（五类根因，174 个接口全覆盖）

| 范围（根因） | 接口数 | 代表接口 | 这一轮做了什么 |
|---|---|---|---|
| 数据库查询：整表 `.all()` / 逐行 XML / 逐字符 bigram | 19 | `getAnnualReport`、`getMomentsInsights`、`getWordCloud` | 收窄扫描面 + 让出事件循环 + 结果缓存（片段上界 2254ms → 3ms 等 23 处） |
| 算法复杂度：O(行数) 的同步循环 | 同上（19 处内的算法改写） | `getAssetInsights`、`planOriginalFetch` | 按行数而非按分片让出；先判码点再 slice |
| 缓存：无结果缓存 / 无索引 / 无负缓存 | 62（本地只读）+ 6（图片本地） | `getStorageStats`、`getPrivacyScan`、`getGraph` | 统一 `cachedBySigAsync`（按库文件签名失效）；图片缓存索引化（160 次 stat → 1 次 readdir） |
| 重复调用：分页收集 / 逐条 RPC / 多面板重复取数 | 18（网络）+ 7（导出） | `getArticleCover`（1221 次慢调用）、`exportAllSessions` | 批量接口 1 次 RPC 替代 N 次；页大小 100 → 1000（页内仍每 100 条上报进度） |
| 网络往返 / 模型推理（不可中断） | 18 + 16 | `getRemoteImages`、`analyzeVisibleMessages` | 并发与超时调参（最坏 80s → 16s）；LLM 首 token 15s 看门狗；合批方案实测**更慢 41.8%**，否决 |

### 1.2 目标（三级，从工程指标到用户视角）

| 层 | 指标 | 目标 | 现状（本机实测） |
|---|---|---|---|
| ① 不拖累别人 | **片段上界** = 总耗时 ÷（让出次数+1） | **≥200ms 的整段独占 = 0 个** | ✅ 0 个；>50ms 的 3–5 个（都在 150ms 内，逐个查过来源） |
| ② 面板利索 | 热跑（缓存命中） | ≤ 5ms | ✅ 多数 0ms；`probe-perf` 29 接口热跑 ≤ 25ms |
| ③ 用户视角 | **点击 → 正文出现** | ≤ 1200ms/面板（预算） | ✅ 14/16 面板 **505–549ms**；2 个已登记队尾 60s（见 §四） |

### 1.3 验证方式（可复跑，缺一条都不算通过）

```bash
npm run coverage:check            # 174 接口 + 36 页签的覆盖矩阵与源码一致（约 1s，可进 CI）
npx vitest run src/backend/wechat-data/tests/query-yield-discipline.spec.ts   # 让出纪律（tick 下界）
npx vitest run src/backend/wechat-data/tests/guard-coverage-ledger.spec.ts    # 每处修复都有守卫
npx vitest run src/backend/wechat-data/tests/cache-timing-coverage.spec.ts    # 缓存覆盖
npm run ui:interactive-budget     # 逐面板"点击→正文"预算（真机，前置 ui:stress）
npm run audit:ledger              # 文档/引用/命令/数字自检（12 类）
```

**门禁的"缺登记 ≠ 通过"**：`interactive-budget` / `theme-contrast-budget` 对"测量里出现
却没登记"的面板一律报错 —— 新面板不会自动免检。

## 二、主题：页面 / 组件 / 切换场景

### 2.1 要覆盖的页面：**36 个**（16 侧栏可见 + 20 隐藏深链）

覆盖方式从"导航里能点到的 16 个"扩到**全部 36 个**：
`npm run theme:live-audit -- --all-tabs` 对隐藏页签写 `location.hash` + reload 进入
（4 个以「设置」弹窗打开，探针**取弹窗本身**而不是它背后那一页 —— 修正前它们复制的是
「数据总览」的读数）。逐页签结果见 [`THEME-COVERAGE-MATRIX.md`](THEME-COVERAGE-MATRIX.md) §1。

**本轮真机结果**：36 个页签 × 2 套主题，**背景未随主题变化 = 0 个**。

### 2.2 要覆盖的组件：10 个族

### 2.4 本轮在主题上真正改了什么

| # | 改动 | 为什么 |
|---|---|---|
| T1 | 真机审计**覆盖 36 个页签**（此前 16 个），并修正弹窗页签的取样根 | 20 个隐藏页签此前是主题盲区；不修取样根，4 个弹窗页签量的是背后那一页 |
| T2 | 对比度从**每面板一个点**升级为**多采样**（面板内全部可见文本，按 `(color,背景)` 去重，上限 40 对），并区分**正文类**与**弱化文字**（`--nm-text-3`） | 单点采样答不了"正文是否 ≥AA"；混在一起则门槛永远卡在弱化文字的 3.75，什么都发现不了 |
| T3 | 修正**渐变/图片底**的假阳性：文字与最近不透明色之间夹着 `background-image` 的对记 `n/a` | 霓虹皮肤（总览）的卡片是透明 + 自己的渐变，此前被算成"白底白字 = 1.10" |
| T4 | 新增判据：**未读徽标白字 on 微信官方红 `#fa5151` = 3.30**（两套主题同值），按棘轮登记 | 真机多采样才第一次量到它；它是官方未读色，与自方气泡绿同类取舍 |
| T5 | `theme-contrast-budget.json` 的例外表**只剩一条**：`聊天会话|dark = 3.30`（微信官方未读红，与 T4 同一对色） | 多采样之后，正文类最低对比度只有这一处低于 AA，且它是官方色值的保真取舍；其余 71 组（36 页签 × 2 主题）全部达标。反向检查仍在：哪天它 ≥AA 就必须删掉这一条 |
| T6 | **修掉"数据总览浅色下仍是深底"**（用户报障）：`overview-neon.module.css` 的 13 条浅色规则原来写裸 `:root.theme-light`，被 CSS Modules 当作本地类名哈希成 `:root._theme-light_18lio_395 …` ⇒ 选择器永不匹配、**整段覆盖是死规则**。改为 `:root[class~='theme-light']`（属性值不哈希）后，浅色下卡片实测 `linear-gradient(158deg, rgba(255,255,255,.9), rgba(244,248,252,.84))` | 这是"写了 ≠ 命中"的典型：字符串层面类名都在，构建/类型/SSR 全绿。新增两条常驻判据：**module CSS 里的 `theme-light` 必须包在 `:global(…)` 里或作为属性选择器的值**；**浅色块里的实色必须是浅色**（`light-theme-coverage.wiring.spec.ts` 第 6/8 条，均含反例自证） |
| T7 | **修掉"数据总览顶部指标牌在浅色下仍是深色、数字看不见"**（同日第二个报障）：① `.plateFace::after`（内嵌玻璃面）是**独立的深色层**，只改 `.plateFace` 改不动它 ⇒ 补浅色白玻璃 + 三种色调的淡玻璃牌面；② `.plateValue` 浅色规则用 `background` 简写改了渐变，**把 `background-clip: text` 重置成 `border-box`**，而 `-webkit-text-fill-color: transparent` 继续生效 ⇒ 渐变铺满盒子、数字隐身 ⇒ 在浅色的两条 `.plateValue` 规则里重新声明 clip 与 text-fill | 两条都是"**量单个元素会以为已经跟主题走了**"的形状。新增判据：**深色端用 `background-clip: text` 的规则，其浅色覆盖必须重新声明它**；**深色端画了深底的 `::after`/`::before`，浅色块必须有同名覆盖**（`light-theme-coverage.wiring.spec.ts` 第 10/12 条，各带反例自证，用纯函数解析规则） |

## 三、一句话总结

- **性能**：174 个接口逐个归入 9 个家族，每个家族都写明**范围/目标/验证**；
  用户视角"点击→正文"14/16 个面板稳定在 **505–549ms**（预算 1200ms），
  ≥200ms 的整段独占 **0 个**。
- **主题**：**36 个页签 × 2 套主题**真机全覆盖，背景未随主题变化 **0 个**；
  正文类对比度全部 ≥AA，仅有的两条低于 AA 的都是**微信官方色值的保真取舍**（已按棘轮登记）。
- **仍有未闭环**：年报首次冷跑 ~2.5s、连点页签后的 60s 队尾延迟、
  `analyzeMessages` 的 ONNX 片段、20–45ms 的有意不动项 —— 全部逐条列在 §四之前与账本第四节。

## 四、已知未闭环（逐条，含为什么不修）

| 项 | 现象 | 结论/原因 |
|---|---|---|
| P-1 | 年报**首次**冷跑仍 ~2.5s（扫约 200 万行） | 缓存只解决"重复查看"（2.5s → 0ms）；降冷跑要改扫描面或落盘缓存，属产品口径 |
| P-2 | 连点 10+ 页签后 `朋友圈洞察`/`收藏与表情` 等 60s | 已定性为"某个后端重活打满一核且与页面无关"，7 个假设已逐个实验排除；**根因未定位**，有门禁（`--stress`）与已知例外登记 |
| P-3 | `analyzeMessages` 片段 ~1187ms | ONNX 单次前向推理，同步不可中断；合批方案实测**慢 41.8%**，已否决 |
| P-4 | 12 个接口 20–46ms 且不让出 | **有意不动**：串行 worker 上用户感知不到，逐模块 async 化的跨模块成本大于收益 |
| P-5 | 探针耗时列本身会漂移（同机同码 250×） | 已写明分档；引用数字请优先用"用户视角"那一列（点击→正文） |
