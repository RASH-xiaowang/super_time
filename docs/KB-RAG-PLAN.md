## 一、核心目标与预期成果

### 1.1 核心目标（一句话）

把「知识库」从**手写笔记的书架**，扩成**你自己的文档底座**：多库并列，每库可容纳条目（笔记）与
文件（文档 / 表格 / 图片 / PDF），文件经解析、分块、向量化后参与**混合检索**（关键词 + 语义），
让问答能引用你上传的东西，而不再只引用聊天记录。

### 1.2 预期成果（可检验，不写「体验更好」这种话）

| # | 成果 | 检验方式 |
|---|---|---|
| G1 | 一个库内可以登记文件，并在界面上看到每个文件的解析状态 | 探针上传 3 个文件 → 状态列为 `ready` |
| G2 | 文件里的内容能被关键词搜到 | 输入夹具独有短语 → 命中该文件 |
| G3 | 文件里的内容能被语义搜到（同义、改写问法也能命中） | 出网开时命中；出网关时降级为纯关键词且**仍能搜到** |
| G4 | 删文件 / 删库**绝不碰用户电脑上的原文件** | 探针断言 `fs.existsSync(src_path)` 仍为真 |
| G5 | 库之间**零串扰**（文件、分块、向量、检索结果都不越界） | 探针切库后文件列表为空；`kb-search.spec.ts` 的不串库断言 |
| G6 | 出网是**可控且可见**的：全局闸门 + 文件级开关 + 审计功能名 | `privacyGate('kb_embed')` 被源码级用例要求出现在 `docs/PRIVACY.md` |
| G7 | 侧栏入口数与可路由页签数的既有契约不被破坏 | 侧栏仍 `16`（图谱/知识图谱并入后已从 17 收敛，T2 加第三段**不得让它再增**）；可路由 `36 → 37` 且四处文案同步 |

### 1.3 明确不产出（与设计稿 §13 的 13 条一致，此处只列会影响排期的）

图片 OCR / 音视频转写 · 多用户与 RBAC · 云同步 · 跨库检索 · 应用内编辑文件正文 · watch 文件夹。

## 三、依赖关系

```
T1 ──> T2 ──> T3 ──> T4
        │
        └──> T5           (T5 与 T3/T4 互不依赖)

T1..T5 全部完成 ──> T6
```

**只有三条硬依赖**（其余都可并行或调序）：

1. `T2 → T1`：没有分块器就没有 `chunk_count`，文件表无从落地。
2. `T3 / T4 → T2`：没有文件与分块表，检索层没有语料。
3. `T6 → T1..T5`：前五步任何一步的失败都会改变「有多少东西可展示」。先做视觉必然返工 ——
   这是把体验层放最后的**唯一**理由。

**可调序的两处**：

- `T5` 与 `T3 / T4` 互不依赖。纯文本族（A/A' 档）已能跑通**全部**检索能力，B 档只是让更多文件
  「能进得来」。所以可以先把 T3/T4 做完拿到完整检索链路，再回头逐个接 B 档解析器。
- `T4` 可以拆成两半交付（先只建库 + 状态，再做检索接入），但**不建议**：那时向量库是个只写不读
  的黑洞，验证不了正确性。

**可独立回退点**：每一步都能单独回退。T1 删文件即可；T2~T5 各自新增独立库与独立 Remote，
删掉新库文件 + 摘掉 Remote 注册即恢复；`notes.ts` 与 `kbs` 表**全程一行不改**。

### 4.1 已识别的「静默失效」类风险（本项目历史高发）

这类风险的共同点是：**typecheck / build / 静态断言全绿，只有功能坏了**。本计划对每一处都安排了
「能咬人的守卫」：

| 静默失效 | 为什么会静默 | 守卫 |
|---|---|---|
| 删掉 `nav-config.ts` 的 `kbfiles` 条目 | 条目 `hidden: true`，不渲染；删了不影响任何渲染路径 | 深链 `#kbfiles` 落回默认页的用例（2026-09-18 真的发生过一次同类事故） |
| 查询漏掉 `WHERE kb_id=?` | 单库测试全绿，只有多库时串数据 | 探针第 7 步 + `kb-search.spec.ts` 的不串库断言（变异测试第 1/2 条） |
| `dialog:open-file` 的钩子没接上 | 原生对话框在无头环境点不到，只是「测不了」 | 探针第 2 步显式设 `SUPERTIME_OPEN_PATHS` 并断言列表出现 3 行 |
| 新依赖没进打包白名单 | 开发态 `node_modules` 里就是有 | T5 验收项 + `package-packaging` 类既有 spec 的思路 |

### 7.1 T1 落地备注（做完之后才知道的事）

**新增文件**：`src/backend/wechat-data/src/query/kb/{types,chunk,parse-plain}.ts`
+ `tests/kb-chunk.spec.ts`（23）+ `tests/kb-parse-plain.spec.ts`（39）。
验收脚本 `working/run-kb-t1.py`，输出 `working/check-output/kb-t1.txt`。

**写测试之前自查出并修掉的 4 个真 bug**（都属「错了也不报」那一类）：

1. `parseHtml` 的 `<br>` **不分段** —— `<br>` 合法且没有斜杠，靠「自闭合」判据不命中，
   一整篇用 `<br>` 分行的文本会被拼成一大段。→ 单列 `VOID_TAGS`。
2. 标题栈用 `slice(0, level-1)` 会在「首行就是 `<h2>`」时产生数组空洞 →
   面包屑变成 `' › 二级标题'`。→ 改定长 6 槽。
3. `tableText` 重排后 `a,"x,y"` 变 `a,x,y`（**两列合成一列**）→ 加按需加引号 + 可逆性断言。
4. HTML **正文**漏解实体（只有标题那一支解过）→ `&amp;` 让「A & B」在 BM25 里变词项 `amp`。
   顺带发现 `normalizeTable` 写了**没人调用**（csv 路径完全没过归一化）。

**两处刻意偏离设计稿**（源码注释里已写明，免得后人当写错）：
① 「续 N」给**所有**非首块（设计稿只说硬切块）；
② 表格块允许超过 `CHUNK_MAX_CHARS` —— 超长来自单行，兜底只能劈行，而劈行正是要避免的。

**一个计划时没想到的取舍**：切点取「断点之后一位」，故按段落切的块**以 `\n\n` 结尾**。
已写成正式断言 ⇒ 它是契约而非巧合。

**顺带补的基础设施**：`working/run-spec.py` 原先只有 `--tsc`（= `typecheck:client`），
**后端没有类型检查入口**，已加 `--tsc-server`。后续每个任务的验收都要用它。

### 7.3 T3 落地备注（做完之后才知道的事）

**新增 / 改动文件**

| 文件 | 角色 |
|---|---|
| `src/backend/wechat-data/src/query/kb-search.ts`（255 行） | FTS5 稀疏检索（**读路径**）。与 `kb/**`、`kb-files.ts` 平级：`kb-search.ts → kb-files.ts`（复用 `openStore`）与 `→ search.ts`（复用 `ftsPhrase`），反向无引用 ⇒ 无环 |
| `src/backend/wechat-data/tests/kb-search.spec.ts`（21 用例 / 5 组） | 真跑 SQLite：跨库隔离、短语命中、`topK` 边界（0 / 负数 / `NaN` / 超大）、空查询与纯标点查询 |
| `src/client/ui-wechat/src/client/pages/wechat-data/panels/kb-delete-copy.ts`（12 用例） | 删库弹层 / 回执的**文案纯函数**（见下） |

**为什么是第三个文件，而不是塞进 `kb-files.ts` 或 `kb/**`**
① `kb/**`（`chunk.ts` / `parse-plain.ts`）的约定是**零依赖纯函数**，而检索要开库、要碰盘，放进去就破了那条约定；
② `kb-files.ts` 是**写路径**（登记 / 删除 / 恢复），检索是**读路径**，且它是唯一需要
「把两个域 join 起来」的地方（`kb_chunks` × `kb_files` × FTS）。平级的第三个文件让依赖单向、也不会有
「检索改动拖垮写路径」的耦合。

**一条刻意留下的「单点」**
本文件唯一硬不变量：**每一处查询都必须带库过滤，且只允许有一处**。
只写一处不是为了省事，而是为了让「漏掉过滤」**可被变异测试咬到** —— 若在 `JOIN kb_files`
上也补一句 `f.kb_id = ?`，那么删掉 `c.kb_id = ?` 时结果**依然正确**，护栏从此再也测不出问题，
而它真正失效的场合（未来某次重构）没有人会发现。`kb-search.spec.ts` 的跨库用例专门吃这一条。

**降级是「此刻的正常态」，且必须被看见**
向量库在 T4 才落地，所以 T3 的**每一次检索都是降级态**。这里不假装有稠密通道，而是把
「为什么只有关键词」如实回报给界面（设计稿 §6.3：降级必须被看见）—— 真机探针里有一条断言
专钉结果区标题写出了实际通道与用时。T4 接上稠密通道只需往 `channels` 里加一员，形状不动。

**参数**：`DEFAULT_KB_TOP_K = 20`（远小于消息检索的 400 —— 单元是**文件块**，一块最长 500 字，
20 条已铺满一屏可读内容）、`MAX_KB_TOP_K = 100`（防调用方传一个把界面拖死的数）、
`KB_SNIPPET_RADIUS = 60`。

**顺手修掉的一个真机缺陷（T3 计划外的收获）**
真机探针第一次跑就撞见：库里有 **2 个文件**时，**删库弹层说「这个库里没有笔记也没有文件」**，
点「一并删除」把分块 / 关键词索引 / 向量 / blob 副本一起清掉却**没有任何回执**，
也**不给「移到别的库」这条路**。根因有两层，缺一不可：

1. `KbMeta` 只有 `noteCount`，而文件登记在**另一个库文件**（`wechat_kb_files.db`，与
   `wechat_notes.db` 并列）里，`notes.ts` 的 `listKbs()` 根本看不到它 ⇒ 真值**只能**由
   `gateway.getKbs` 把两个库文件合流后给出（`countKbFilesByKb()` 一次 `GROUP BY`）。
2. 即便合流对了，**文件增删也没有让库列表缓存失效**：`invalidateKbFileCaches()` 只清
   `kb-files:<id>`，而 `fileCount` 住在另两套缓存里（`KB_LIST_CACHE_KEY` 快照层 + `kbs-`
   渲染层）⇒ **已经挂载**的切换器手里仍是旧数组。所以文件变更统一改走 `invalidateKbCaches()`
   （一次做全三件事：清快照 + 清渲染缓存 + 广播 `KBS_UPDATED_EVENT`）。

设计稿 §10 边界 7 要求的「N 个文件与目标库内容重复，未迁移」由 `deleteReceipt()` 逐字给出；
`movedFiles` / `removedFiles` 的 `undefined` 与 `0` **分开说**（前者＝文件侧没清点成，
后者＝清点过、确实没有）—— 混成一句就是把相反的两件事说成同一件。
文案之所以抽成纯函数：本仓库没有组件测试环境，写在 JSX 里就只能做源码级文本断言，
那只能证明「串还在」，证明不了「0 个文件时说的是什么」。
