## 测量口径（三条，必须一起读）

1. **让出次数**：用仓库自己的 `startTickProbe()`，契约写在 `src/backend/tests/helpers/tick-probe.ts:13`
   —— `ticks == 让出次数 + 1`。同步函数拿 0 tick 是**预期**，那正是"整段独占"的形状。
2. **片段上界** = `总耗时 / (让出次数 + 1)`。这是**上界**不是精确值；`让出 = 0` 时即"整段独占"。
   **串行 worker 上，别的请求最多要等的就是这个数**，而不是总耗时。
3. **冷跑**：每次测量前 `invalidateWechatMeta()` 逼出冷算，否则量到的是缓存命中。

⚠️ **四个已踩过的测量/操作陷阱**（读本账时必须知道）：

- **① 残留 Electron 进程会污染计时（2026-09-29 发现，尤其重要）**：实测清理时发现
  **20 个残留进程、累计 4978s CPU、约 3.9GB 常驻**，其中两个主进程分别烧掉 **1739s**
  与 **712s** CPU；重型进程是 **backend worker**（`utility` 角色）。
  后果是**所有计时类判据被污染**：`ui:panel-audit` 每张截图从约 **12s** 拉长到
  **11 分钟**（约 55×）；清掉残留后立刻恢复 12s。

  **来源已排查（同日）**：入仓的三个工具**都不泄漏** ——
  `theme-live-audit`（普通）、`theme-live-audit --stress`、`panel-audit`
  在「正常跑完」「`job_kill` 打断」「超时提升为后台任务后打断」三种收尾路径下，
  残留数都回到 **0**。那 20 个来自**我自己早前那些一次性诊断脚本**
  （`working/diag-*.mjs` 等），它们的 node 父进程在异常/被打断时没能跑完 `finally`，
  于是 Electron 子进程成了孤儿，并在后台持续烧 CPU。
  ⇒ 教训：**真机实验脚本必须保证异常路径也 `app.close()`**；跑计时类判据前先数一遍进程。
  ⇒ `npm run ui:verify` 会在开头/结尾各数一次并告警（运行前 >5 个就提示读数不可比）。
  ⇒ 也因此，本账里**受污染风险最高的那条（队列深度 / 60s 延迟）已在 0 残留进程的
  干净机器上复现**（见第三节五）；其它纯耗时数字按"可能偏慢"理解 ——
  这个方向是保守的（真实性能只会更好，不会更差）。

- **② 截屏不可当判据**：同一时刻截图显示骨架屏 + 首次配置向导，DOM 探针却报
  `nm-skel=0`、无 dialog（2026-09-29 实测）。主题一致性的证据因此用 **computed style**，
  不用截图。

- **③ 真机脚本必须写 `wechat/config.json`**：临时 profile 里漏了它，应用就没有数据根，
  面板只画标题与标签、**一个数值都没有** —— 这个状态极易被误读成"面板卡住/取数失败"。
  正确姿势见 `scripts/panel-audit.mjs:32-41`（带前置断言）。

- **④ 用 PowerShell 的 `Set-Content` 批量改文件会**写入 UTF-8 BOM**（2026-09-29 踩到）**：
  PowerShell 5.1 的 `Set-Content -Encoding UTF8` **默认带 BOM**，而仓库有守卫
  `src/backend/tests/source-text-integrity.spec.ts` 要求**源码无 BOM**（BOM 会让"第一行"的
  文本类判据对不上）。本轮改 `scripts/panel-audit.mjs` 时中招，守卫立刻报红：
  `每个文件都是合法 UTF-8 且没有 BOM`。
  ⇒ **经验**：批量文本替换优先用编辑器工具（`edit` / `write`），别用 `Set-Content`；
  万一用了，改完**检查头三个字节是否为 `EF BB BF`** 并剥掉。
  （本轮只此一个文件中招，其余脚本/文档复查均无 BOM。）

### 1.0.1 交互式口径已加**紧门禁**（2026-09-29 第 82 轮）

**问题**：`--stress` 自带门槛 **3000ms**，而基线 **504–554ms** —— 那是**有意留给慢机器**的 5.8× 余量。
代价是"**~520ms 涨到 2500ms**"这种温水式退化**不会被任何东西发现**。而这组数是
**唯一可信的用户视角指标**（不依赖第 73/74 轮那条不稳的 tick 探针耗时）。

**做法**（门槛与测量分离）：
1. `theme-live-audit.mjs --stress` 现在把逐面板耗时**落盘**到
   `.tmp-e2e/interactive-timings.json`（此前只打印到控制台 ⇒ 没有任何门禁能核对）；
2. 新增 `scripts/interactive-budget.json`：**默认预算 1200ms**（基线 504–554ms ⇒ **2.2×** 余量，
   足以容忍慢机器与抖动，又能抓住温水式退化），并对两个已登记队尾面板单独给 61000ms；
3. 新增 `npm run ui:interactive-budget` 逐面板核对。**缺登记 ≠ 通过**：
   面板出现在测量里却不在预算里 ⇒ **报错**（否则新面板会自动"免检"）。

**实测 + 反例自证**：

```
16 个面板（其中 2 个登记为已知慢）；失败 0 项
未登记为已知慢的 14 个：504–554ms（离散 50ms）      ← 紧门禁下的真实数字
=== 全部在预算内（默认 1200ms）===

反例：预算压到 500ms ⇒ 16 个面板全部 **超预算**、退出码 1；还原 ⇒ 通过。
```

**为什么门槛写 1200 而不是贴着基线**：这组数来自**真机**（真 Electron + 真数据 + 机器负载），
不是单元测试；贴太紧会把机器抖动当回归（第 57 轮那个"看着在跑其实空转"的反面教训）。
2.2× 是一个**有依据的折中**，不是随手取的。

### 3.2 主题一致性也加了**真机门禁**（2026-09-29 第 83 轮）

**补的是哪个洞**：主题一致性此前有两层离线守卫（`--nm-*` 10 用例、`--wx-*` 8 用例），

**做法**（与第 82 轮的交互式门禁同一套结构：测量落盘 + 预算分离 + 缺登记≠通过）：

### 1.1 交互式实测：**用户视角**的"点击 → 正文出现"（2026-09-29 第 77 轮新增）

前面所有耗时都是**探针**量的（进程内逐方法调用）。第 77 轮改用**用户视角**的口径：
`scripts/theme-live-audit.mjs --stress` 会在连点若干页签后**回访每个面板**，
记录"**点下去 → 正文（>50 字）出现**"的墙钟时间（实现见该脚本 `:261-270`）。

**为什么值得单列**：这一列**不依赖 tick 探针**，所以**不受第 73/74 轮那条"耗时列不稳定"的影响** ——
它是目前唯一可信的、回答"用户到底等了多久"的数据。

| 面板 | 点击→正文 | 面板 | 点击→正文 |
|---|---|---|---|
| 数据总览 | **548 ms** | 资金往来 | **519 ms** |
| 微信问答 | 520 ms | 待办日程 | 517 ms |
| 总结 | 519 ms | 知识库 | 516 ms |
| 聊天会话 | 535 ms | 群聊分析 | 505 ms |
| 通话记录 | 520 ms | 通讯录 | 505 ms |
| 朋友圈 | 535 ms | 隐私体检 | 503 ms |
| 文件与存储 | 506 ms | 操作日志 | 520 ms |
| **收藏与表情** | **60049 ms** | **朋友圈洞察** | **60133 ms** |

**结论（两条，都很干净）**：

1. **14/16 个面板 503–548 ms** —— 离散度只有 **45 ms**（最快 503、最慢 548）。
   这个紧致程度本身说明"面板响应速度是稳定的"，**没有隐藏的长尾**。
2. **那 2 个落在 60049 / 60133 ms**，即 **恰好 60 秒**。这是**同一个已收线问题**
   （账本第 41–46 轮、下方"连点 60s"整节）：**不是这两个面板算得慢**（直连实测 512–516 ms），

## 三点五、「连续切页签 ⇒ 某面板卡在统计中」的实测结论（2026-09-29）

**现象**（真机 + 真实数据，可复现）：**先连续访问约 10 个以上页签**，再点「朋友圈洞察」，
面板正文停在 `统计中…`（4 字）**持续 40–60 秒**，然后一次性出现完整内容。
带 `--stress`（连点全部 16 个页签、每个只停 1.2s）时更明显：16 个面板里 **14 个回访 ~520ms
就出内容，2 个（`朋友圈洞察`、`收藏与表情`）40s 仍未出**。

**排除项**（都做了对照实验，不是猜）：

| 假设 | 实验 | 结论 |
|---|---|---|
| 面板本身慢 | 冷启动后**直接**点它 | **516ms** 出内容 ⇒ 面板不慢 |
| 点击路径相关 | 直接点 / 先点数据总览再点 / 等 10s 再点（三条路径各一次全程观察） | **516 / 512 / 529 ms** ⇒ **与路径无关** |
| 后端队列被**少量**页签塞满 | 先过 2 个重页签再点 | **524ms** ⇒ 2 个不构成影响 |
| 点击没生效 / 渲染错面板 | 逐步记录正文 + 命中页签 | 正文确为 `统计中…`，`panelBody` 存在且只有一个子元素（`_loadingState_`）⇒ **点对了，是加载态没结束** |
| 探针取样太早 | 每格等待 2.5s → 5s | 读数不变 ⇒ 不是"等得不够" |
| 请求失败/被拒 | 观察到 75s | **不报错、无 `role=alert`**，60s 时正常出内容 ⇒ **排队后被延迟执行**，不是失败 |
| 数据到了但没渲染 | 抓 DOM 形状对比（有/无压力） | 压力下 `panelBody` 只有加载态一个子元素 ⇒ **数据确实没到**，不是渲染问题 |
| 面板永久卡死 | 把回访观察窗提到 75s | **60055ms / 60292ms 都出了内容** ⇒ 是**延迟**而非卡死，且延迟上限 = RPC 超时窗口 |

**结论**：`getMomentsInsights` 的本地计算只要 ~0.5s，**那 40–60s 是排在串行 worker 队列里等出来的**。
触发条件是"**先访问足够多的面板**"（数量级 ~10 个，2 个不够）——这些在途请求
**不会因切走而取消**，于是后来的请求排到队尾。60s 这个数字与 RPC 默认调用超时
（`src/backend/backend-rpc.js:18` 的 `DEFAULT_CALL_TIMEOUT_MS`）**逐秒吻合**，
属于"刚好在超时窗口内轮到自己"。

**为什么没修**：那 23 处修复解决的是"**单个**接口从头独占事件循环"（片段上界都压到
百毫秒级）。这条是**队列深度**问题 —— 单个接口快了，但连续访问十几个面板仍会把队列排满。
可行修法（**取消在途请求** / 多 worker / 队列优先级）都是架构级改动，超出"逐接口优化"范围；
且现场日志（`docs/PERF-AUDIT-172-2026-09-28.md` 的 1658 条慢调用）里**没有这个形状**，
我无法证明它在真实使用节奏下会造成同等等待。

**已可复跑**：`npm run theme:live-audit -- --stress` 会打印每个面板的
"连点时正文长度 / 回访出内容耗时 / 连点结束时谁还停在加载态"，并**按下面的门槛进退出码**。

#### 为什么"取消"这条路走不通（2026-09-29 查证）

| 事实 | 依据 |
|---|---|
| worker 是**串行**派发，且**没有取消通道** | `src/backend/wechat-worker.js:72-79` 只有 `case 'call'`，`post({ id, value: await backend.call(...) })`；`backend-rpc.js` 全文**搜不到** `cancel`/`abort` |
| 一旦某个 call 开始执行，它就是**同步跑完**的 | 后端是 `node:sqlite` `DatabaseSync`，单次调用内部整段不交还事件循环 |
| IPC 这条路径**不传 `AbortSignal`** | `preload.js:42` `call: (method, args) => ipcRenderer.invoke('wechat:call', method, args)` —— 只有两个参数 |

⇒ 因此"取消"最多只能去掉**尚未开始**的排队项；**对已经在跑的那个 call 无效**（它无法被中断）。
而积压的主体恰恰是"**已经排上队、worker 正在一个一个做**"的请求。

**已排除的干扰项**：`wechat-worker.js:40` 有一个「永不回包」调试注入
（`SUPERTIME_DEBUG_HANG_METHODS`，**只在 `loading-recovery-e2e.mjs` 里用**，打包态主进程会删掉该变量）。
它的形状与本次现象**高度相似**（worker 不回包 ⇒ 主进程按 60s 超时预算收敛），所以必须排掉：
本机该环境变量为**空**，我的真机脚本也未设置它 ⇒ **不是它造成的**。

#### 真正的原因（**后已被推翻，见下**）：同一个面板会反复重发请求，堆在串行队列里

`useWechatDataUpdated(handler)`（`hooks.tsx:147`）是一个**数据落地事件**：冷启动同步期间
（本文件名注释记着实测"约每 10 秒一次"）会反复触发。各面板的用法**有无守卫并不一致**：

| 面板 | 写法 | 在途时再来事件会怎样 |
|---|---|---|
| `MomentsInsights.tsx:49` | `if (!data) void load()` | **再发一次**（`data` 仍为 null，load 也无在途守卫） |
| `AssetInsights.tsx:41` | `if (!data) void load()` | 同上 |
| `MediaAssets.tsx:44` | `void load()` **无任何守卫** | 每次都发 |
| `KnowledgeBase.tsx:183` | `void load()` **无任何守卫** | 每次都发 |
| `GroupInsights.tsx:64` | `if (groups.length === 0) …` | **有守卫**（正例，说明这个坑是被认识到的） |

而 `load()` 一进来就 `setLoading(true)`、**没有"已在途"判断**。于是同步期间
"每 10 秒一次事件 × 无守卫的面板"会在串行 worker 上堆积同一份重查询；
用户再切页签，新请求就排在**这一堆**后面 —— 60s 正是排队等到超时窗口的读数。

**可动的修复（按风险从低到高）**：
1. **给 `load()` 加在途守卫**（如 `if (inflight.current) return`）—— 纯客户端、可确定性验证、
   不动 IPC；
2. **给各面板的 `useWechatDataUpdated` 统一加节流/去重**；
3. 贯通 `AbortSignal` 到 worker（**收益有限**，因为拦不住已在跑的 call）。

**本轮未实施**：第 1 条看起来小，但它会改变多个面板的取数节奏，而"冷启动同步期该重试多少次"
本身是个产品口径问题（文件名注释解释了**为什么要重试**：不重试会停在"0 / 暂无数据"）。
我不想在没有覆盖各面板回归用例的情况下改它 —— 留作下一轮，先补一条能观测"同步期各方法被调用次数"
的量具（这是验证第 1 条是否有效的前提）。

#### ⚠️ 上述根因**尚未证实**（2026-09-29 两次量具都失败）

它是**静态阅读代码 + 现象对照**得出的假设，我尝试量化但两次都失败，**不能算证据**：

**结论**：**根因待证实**。在上述现象被量化证实之前，不应据此改代码。
（现象本身是硬的：真人节奏 14/16 面板 ~520ms、2 个 60s，且这 2 个恰是"离开时内容未到"的 ——
这部分已复现多次。）

#### 第 41 轮：又找到两条**削弱**该假设的证据（继续不修）

| 发现 | 依据 | 对假设的影响 |
|---|---|---|
| 实时同步**每 10s 一次**（注释与常量一致） | `sync.ts:33` `SYNC_INTERVAL_MS = 10_000`；`gateway-core.ts:202` 注释"每个约 10s 一次的同步事件" | 与假设一致（这部分成立） |
| **同步 tick 有重入保护** | `sync.ts` 的 `tick()` 首行 `if (running) return` | 同步**自身**不会堆积 ⇒ 堆积只能来自**面板侧**的重发 |
| **我的测试 profile 没设 `db_dir`** | `gateway-core.ts:196-199` `rawDbDir()` 读 `getConfig(decrypted)['db_dir']`，我写的 `config.json` 里没有这个键 | ⚠️ **实时同步在我所有真机测量里可能根本没跑** ⇒ "每 10s 一次同步事件"**不是**我测到的 60s 的原因 |

**算一下量级（用已测数字，不靠猜）**：`getMomentsInsights` 冷跑 ~520ms。
60s ÷ 520ms ≈ **115** 个排在前面的请求。若真由"每 10s 一次事件 × 少量面板"堆积，
需要同步持续 **≈19 分钟** —— 远超任何一次会话（我的测量会话 ~85–100s）。
⇒ **"同步事件导致的重复重发"不足以解释 60s**，该假设**很可能不是主因**。

**更可能的解释（待验证）**：一次切页签时，面板**同时**发起多个重查询
（`收藏与表情`/`朋友圈洞察` 这类面板会一次拉多项统计），而 worker 串行 ⇒ 排在后面的那个
要等前面全部做完。这与"1.2s 连点比 5s 真人更慢"的观测一致（连点会叠加更多面板的在途请求）。

**下一步（不插桩的判据）**：量**单个面板一次访问发出几个请求 / 总耗时多少**
（用"只点这一个面板、不点别的"对照"点完 15 个再点它"）——
若单面板自己就要几十秒，则与"别面板阻塞"无关，是**该面板自己的取数成本**。

#### 第 41 轮：对照实验做完 —— 当时以为"根因确定了"（**第 43 轮已推翻**）

在 0 残留进程的干净机器上，同一个面板（`朋友圈洞察`）四种条件（每次都全新应用实例）：

| 条件 | 结果 |
|---|---|
| **A** 只点这一个面板（其它页签一个都不碰） | **517 ms** |
| **C** 仅前置「数据总览」（1 个） | **524 ms** |
| **B** 前置 12 个页签，真人 5s/页 | **60153 ms** |
| **D** 前置 12 个页签，连点 1.2s/页 | **60128 ms** |

**四条读出来的结论**：

1. **不是这个面板自己贵** —— 单独访问 **517ms**；
2. **不是"重复重发/同步事件"** —— B 与 D **几乎一模一样**（60153 vs 60128ms）。
   若主因是"每 10s 一次的事件 × 重发次数"，两种节奏（5s vs 1.2s，相差 4 倍）**必然**给出不同结果。
   ⇒ **最初的假设被这个实验直接证伪**（与上一小节的量级算术一致）；
3. **是"前面有足够多的页签"造成的** —— 1 个前置无事（524ms），12 个前置必中（60s）；
4. **60s 与节奏无关** ⇒ 那是**串行队列被前面面板的取数占满**，与请求何时发出无关。

**所以真正的形状是**：前面那 12 个面板各自在**首次访问**时要做若干重查询
（`收藏与表情`/`文件与存储`/`知识库`/`隐私体检` 等都会一次拉多项统计），
它们串行排队；排到后面的请求**要等前面全部做完**，于是撞上 60s 超时窗口。
这与"我每个接口都压到百毫秒级片段"不矛盾 —— 单接口快了，但**首次访问一个面板要做的接口数 ×
12 个面板**加起来仍然可观。**要再降，方向是"减少一个面板首屏的接口数与总成本"，不是"取消请求"。**

#### 第 43 轮：又**连否两个假设**，且证明"启动期"是干净的 —— 至此仍未定位

**① 启动期 worker 其实是空闲的**（逐秒探测轻调用 `getOperationLog`）：

**② 12 个面板的典型方法串行总耗时只有 517ms**（每个单发、缓存命中）：

|---|---|---|

**③ 但走完整序列后，连 `getOperationLog` 都会 60s 超时**（第 42 轮实测，可复现）。
这两件事同时成立 ⇒ **60s 不是"总量大"，而是"某种东西把 worker 卡住了"**
（轻调用也要等满超时窗口 ⇒ 更像**被独占**或**排队去重失效**，而不是"前面有很多活要干"）。

**⚠️ 未定位。四个假设全部被自己否掉**：面板自身贵 ❌ / 同步事件重发 ❌ /
12 面板取数排队 ❌ / 启动期全量解密 ❌。

**已排除项清单（都是实测，可复跑）**：
- worker 启动 ~1s 即可用（2ms）；启动完整解密 t=3s 结束；
- 单独访问目标面板 517ms；轻调用在空闲时 2ms；
- 与点击节奏无关（5s 与 1.2s 给出几乎相同的 60s）；
- 与"哪几个面板"无关，只与"前面够不够多"有关（1 个没问题、12 个必中）。

**下一步该量什么（留给下一轮）**：既然"总活量小"与"轻调用也超时"并存，
就该量**在拥塞期间 worker 到底在做什么** —— 最直接的是 **CPU 占用曲线 + 是否在忙轮询**：
第 36 轮曾观测到 utility 进程在 10 分钟内累计 **891s CPU**（≈ 148% 单核占用持续 10 分钟），
这个数字本身就是"worker 被某个循环占满"的形状，而不是"偶尔做个查询"。

#### 第 44 轮：**量到了** —— worker 被打满且**不恢复**（现象定性完成）

同时采两条曲线：utility 进程的 ΔCPU，和轻调用（`getOperationLog`，空闲时 1–2ms）的往返。

```
阶段 1 空闲基线：轻调用 1ms, 2ms, 1ms, 1ms, 1ms    utility ΔCPU = 0.0s / 10s（≈0%）

阶段 2 连点 16 个页签（1.2s/页），每 3s 采一次：
  + 0s   4%    轻调用 1ms   ok=Y
  + 3s   4%    轻调用 1ms   ok=Y
  + 6s  31%    轻调用 超时      ← 拐点：从这里开始
  + 9s 108%    轻调用 超时
  +12s 107%    …
  …（直到 +57s 一直是 96–109%，轻调用**全部超时**）

阶段 3 连点**已结束**，继续观察 60s：
  + 6s…+60s  utility ΔCPU = 6.0–6.8s / 6s（≈101–113%），轻调用**仍然全部超时**
```

**判读（三条，都硬）**：

1. **CPU 饱和 ⇒ 不是"在等锁/IPC"**，是 worker 真的在**满负荷跑**（~101% 单核持续）；
2. **拐点出现在连点开始后约 6s**（前 6s 还是 4% + 1ms）⇒ 由**某次页签访问**触发，
   不是启动就有；
3. **连点结束后 60s 仍然 100% 且轻调用全部超时 ⇒ 它不恢复**
   （累计已超过 2 分钟满负荷）。

⇒ 这不是"排队等前面做完"（那样 CPU 会降下来），而是**一个不会结束的重活**
（要么是极长的同步计算，要么是**不收敛的循环/重试**）。
**至此"现象定性完成"**：`连点页签 → 某个后端操作进入长时间满负荷、且不自行结束`。

**下一步该定位是哪一个操作**：拐点在 t≈6s，对应第 3 个页签附近（`总结`）。
最直接的做法是**二分**：只点前 N 个页签、观察是否出现 CPU 饱和，逐步缩小到单个页签；
再在那一页的方法集合里找"可能不收敛"的实现（如无上限的重试/递归/遍历）。

其余 14 个页签单独点都是 0% + 1–2ms。

这同时解释了第 41 轮"前置 1 个没问题、前置 12 个必中"：那 12 个里包含这两个面板；
只要它们被访问过，worker 就**持续**满负荷，之后所有请求都只能等超时窗口。

**一条很可能就是原因的代码路径**（`朋友圈`，**尚未确证**）：

`panels/moments-panel.tsx:150-163` 的懒加载观察器把自己的依赖写成了 `moments.length`：

```js
useEffect(() => {
  const el = moreRef.current
  if (!el || typeof IntersectionObserver === 'undefined') return
  const ob = new IntersectionObserver((entries) => {
    for (const e of entries) {
      if (e.isIntersecting && !moreInFlight.current && moments.length < total) {
        moreInFlight.current = true
        void load(false).finally(() => { moreInFlight.current = false })
      }
    }
  }, { root: scrollRef.current, rootMargin: '400px 0px' })

  return () => { ob.disconnect() }
}, [moments.length, total, load])       // ← 每次加载都重建观察器
```

而 `load(false)`（`moments-data.ts:95-99`）会 `apiGetMoments({limit, offset})`、
把 `countRef` 往前推、并 `setTotal(env.total)`。**若 `countRef` 与 `env.total` 口径不一致**
（例如 `total` 是全量、而 `countRef` 按过滤后累加），`moments.length < total` 会**长期成立**
⇒ 观察器反复重建 + 重建后立即再次命中 + 再次 `load` ⇒ 对 worker 的**不间断请求流**。

**下一轮该做的（两件都小）**：
1. **确证**：只点「朋友圈」，持续采 CPU 与请求量，确认请求是否在无限增长（增长 ⇒ 就是它）；
2. **修**：把观察器依赖收窄（`moments.length` 改从 ref 读，不进依赖数组），
   并给 `load(false)` 加"本页返回 0 条即停"的终止条件。

**当前结论（比上一轮更硬、也更开放）**：
`朋友圈` / `收藏与表情` 的**首次访问会启动一个不受页面生命周期约束的后端重活**，
它打满一核、持续（实测 ≥2 分钟）不归还，于是所有后续 RPC 只能等超时窗口。
**具体是哪一个重活仍未定位** —— 已排除：前端翻页循环、单方法自身耗时、启动期解密、总活量。

**下一轮的方向**：既然它**与页面无关且不结束**，就直接抓它**在跑什么代码** ——
给 worker 进程取 **CPU profile / 栈采样**（`node --cpu-prof` 或 `process.report`
可在 utilityProcess 里启用），从热点函数名直接读出循环位置。这比继续在外面猜直接得多。

这也正好绕开前几轮"渲染层被 contextBridge 冻结、`ipcMain.emit` 不是派发路径"两个插桩障碍。

**② 又排除一个很像的候选**：`apiDecryptAllDatabases`（"解密**全部**数据库"，

**不在任何面板的挂载路径上** ⇒ ❌ 不是它。

**至此已排除 7 项**：面板自身贵 / 同步事件重发 / 12 面板取数排队 / 启动期解密 /
前端翻页循环 / 单方法自身耗时 / `apiDecryptAllDatabases`。**根因仍未定位。**

**⚠️ 我的判断：这条线该收敛了。** 连续 6 轮（41–46）投入在这个"连点页签后
2 个面板 60s"的现象上，每轮都在**排除**而不是**定位**，且它：
- 有**门禁**（`--stress` 3s）在管、有**已知例外**登记，不会静默退化；
- **现场日志里没有这个形状**（`PERF-AUDIT-172` 的 1658 条慢调用）；

任何人接手都能从第 46 轮的状态直接往下走。

#### 第 42 轮：找到了更上游的占用源（但第 43 轮又把它否掉了）

**工具层面**：发现**应用自己的操作日志就带 `durationMs`**
（`query/operation-log.ts` 读出 `rawMs`，注释明确"不要归一成 0"），
所以"接口耗时"这类问题**本来就有免插桩的量具**（`getOperationLog`）——
比我这三轮折腾的插桩都省事。记下来免得下次再绕。

**但用它量的时候撞到了更硬的证据**：走完 16 个页签后调 **`getOperationLog` 本身也 60s 超时**：

```
Error invoking remote method 'wechat:call': Error: 调用超时（60 秒未返回）：getOperationLog
```

一条"读日志"的轻调用都要等满 60s ⇒ **worker 在整段序列结束后仍然被占着**，
说明占用源**不只是面板的取数**。

**上游占用源（主进程日志实证）**：启动 **t=3s** 时有一次
`[wechat-sync] updated: biz_message_0.db:full(2518p/w0), message_0.db:full(11876p/w0), message_1.db:full(37456p/…)`
—— 关键词 `full` = **全量重解密**（`sync.ts` 的 `mode: 'full'` 分支），
涉及数万页、且解密派生密钥是重活（现场日志里 utility 进程累计烧掉 **4978s CPU** 与此一致）。

**并且它只发生一次**：150s 观测窗内 sync 事件**共 1 次**（t=3s），之后收敛。
⇒ 所以之前"每 10s 一次事件"的注释描述的是**数据变化的常态**，
而**启动那一次 `full` 才是这轮测到的重头**。

**综合后的完整形状**（把两轮证据合起来）：
1. 启动 t≈3s 起，worker 进入**一次全量重解密**（重、同步、不可中断）；
2. 与此同时用户开始点页签，各面板的取数请求**排在它后面**；
3. 连点（1.2s/页）会在解密还没结束时又叠上 12 个面板的请求 ⇒ 队列更深；
4. 排到队尾的请求（如 `朋友圈洞察`）要等前面全部做完 ⇒ 撞 60s 超时窗口；
5. 只点 1–2 个页签时队列浅，解密窗口内也能很快轮到自己（实测 517–524ms）。

**为什么仍未修**：这不是"某个接口慢"，而是**启动期一次全量重解密与首屏取数争抢同一个串行
worker**。可行的方向（把初始全量解密延后/降优先级/只在空闲时做、或让首屏查询优先）
都属**调度策略**改动，会牵动"实时同步多久能看到新消息"这个产品口径 ——
不应在没有产品决策的情况下改。

> ⚠️ **但第 43 轮已经把上面这一整套否掉了**：实测 worker 从 t=1s 起就在毫秒级响应
> （启动期是干净的），12 个面板的典型方法串行总耗时也只有 517ms。
> 所以本小节连同它上面的"12 面板排队"说法**都只是被后续实测推翻的中间结论**，
> 保留在此仅为记录推理链。**当前状态：未定位。**

   启动 **t≈3s 起有一次全量重解密**（`[wechat-sync] updated: …:full(37456p/…)`，
   150s 内只发生 1 次），首屏取数请求**排在它后面**。

   **2026-10-08 的发现：那次全量重解密在多数情况下根本不该发生。** `sync.ts` 的 `lastState`
   是**进程内存里的 Map**，后端一重启就空 ⇒ 每个目标 `prev === undefined` ⇒ `mode` 一律判
   `'full'` ⇒ **每次冷启动都把全树整库重解密一遍，哪怕微信侧一个字节都没变、磁盘上的解密产物
   已经是新的**。而签名只对**原始文件**算，从不与**已解密产物**比对（`SUPERTIME_SYNC_TRACE=1`
   的诊断里那条 `原因=prev=undefined(首次)` 就是它自己报出来的）。

   **改法**：新增 `src/backend/wechat-data/src/query/sync-state.ts`（落点 `<数据根>/sync-state.json`），
   记下「哪个目标的源签名已成功解密」，首 tick 播种进 `lastState`。
   **判定逻辑一行没改** —— 源没变命中既有 `continue`（零工作量）、只有 WAL 变仍走既有 `'wal'`
   增量、��库变了仍走 `'full'` ⇒ **实时同步的新鲜度与节奏完全不受影响**（本轮产品口径：
   新消息同步延迟 < 30s），受益的只有「启动不必白解一遍」。
   落盘只取 `takeSyncSuccesses()` 那个**成功子集**，绝不直接写 `lastState`（后者是乐观记录的，
   失败那条路会保留签名 ⇒ 会把没解成功的目标也标成「已解密」，下次启动跳过它 ⇒ 永久旧数据）。

   **失败方向每一条都倒向「把活干完」**：账本读不出来 / 版本不认识 / 条目形状不对 / 产物被删
   ⇒ 一律回到整库重解密。少解一遍只是慢几秒，跳过一次却是永久显示旧数据且没有提示。

   **判据**：`tests/sync-source-state.spec.ts` 9 项（合成 SQLCipher4 页，跑真实同步回路，
   以 `onSync` 是否被回调当「有没有真干活」的行为观察点）+ `tests/sync-source-state-wiring.spec.ts`
   9 项（AST 接线 + 棘轮）。**变异自证 3 处全部 RED-OK**：去掉播种 / 去掉版本检查 /
   把落盘循环改成直接迭代 `lastState`。其中「版本检查」那一处**第一版没咬住**——
   夹具写的是 `entries: {}`，空 entries 下删掉版本检查与保留它加载结果都是空 Map ⇒ 恒绿；
   改成把第一轮真实签名装进错版本后才咬住（判据不承重时，变异自证是唯一的照妖镜）。

   **这一轮没修掉的（说清楚免得读成收工）**：**真需要一次全量解密时，队列深度问题原样存在** ——
   首次启动、微信真写了主库、或产物被删，这三种情况仍然会让首屏请求排在解密后面。
   修那一半仍要动调度策略（把解密切片让给首屏查询），那才会牵动"实时同步多久能看到新消息"的产品口径。
   另：只读查询并行化（`QUERY-PARALLELISM.md`）仍是**设计（未实施）**，本轮没碰。

**为什么不硬修**：这三个都在 130ms 以内、都是**用户主动触发**的操作（"自动获取密钥"），

**改造成本 > 收益**，这与"20–45ms 有意不动"是同一条判断标准。
