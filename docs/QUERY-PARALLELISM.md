# 只读查询并行化（多线程）设计与验收门槛

> 状态：**设计（未实施）**。2026-09-29 第 33 轮。
> 依据：第 32 轮真机测量。**没有测量支撑就不动取数层** —— 这份文档就是为了避免凭直觉重写。

## 1. 问题：现在的取数是"单线程串行"，而且它是 CPU 密集

真机（真实数据副本，逐条跑四个最重的查询；`cpu` = `process.cpuUsage()` 增量，含进程内所有线程）：

| 查询 | wall | cpu | cpu/wall |
|---|---|---|---|
| `getWordCloud(2026)` | 899 ms | 1250 ms | **1.39** |
| `getStorageStats` | 113 ms | 110 ms | 0.97 |
| `getOverview` | 75 ms | 109 ms | 1.45 |
| `getOverviewInsights` | 258 ms | 281 ms | 1.09 |
| **串行合计** | **1345 ms** | 1750 ms | **1.30** |

**判读**：`cpu/wall ≈ 1.0–1.45` ⇒ 时间花在**算**上，不是在等 I/O。
因此并行化的收益形状是 `串行总和 → 最慢的那一个`：这四条上 `1345ms → 899ms`，
**上限省 446ms（33%）**；查询越多、数据越大，收益越大。

**为什么现在并行不了**：

- 后端是**单 worker 进程**，查询在同一个 JS 线程上跑；
- SQLite 用的是**同步 API**（`node:sqlite` 的 `DatabaseSync`）⇒ 一旦开始执行就占住线程；
- 所以客户端同时发 4 个查询时，`Promise.all` 只是**排队**，总耗时仍是各自之和
  （这正是巡检里"接口总耗时 ≈ 各接口耗时相加"的原因）；
- 比值 >1 只是因为 V8 自己的 GC/编译线程也在工作，跟我们的查询无关。

## 2. 设计：只读查询 worker 池

```
主 worker（现有 wechat-worker.js）
 ├─ 写路径 / 配置 / 解密 / 导出        ← 保持单线程，绝不能并发（数据一致性）
 ├─ 结果缓存 + 签名缓存（进程内）      ← 保持在这里，worker 无状态
 └─ 只读查询池（worker_threads，N = min(4, 核数-1)）
      ├─ worker #1  ← 自己的一套只读 SQLite 连接
      ├─ worker #2  ← 另一套（连接不能跨线程共享）
      └─ …
```

**关键约束（每一条都会决定成败）**：

1. **连接不能跨线程**：每个 worker 必须自己 `new DatabaseSync(..., { readOnly: true })`。
   好处是顺手满足"每个 worker 一套句柄"的纪律；代价是**句柄数与内存随 N 增长**
   （Windows 上句柄泄漏会让目录删不掉，见 `query-db-lifetime.spec.ts` 的说明）。
2. **只有"纯只读、无副作用、可重放"的查询能进池**：例如 `getWordCloud`、`getStorageStats`、
   `getOverviewInsights`。凡是写库/改配置/建索引/解密的，一律留在主 worker。
3. **缓存仍在主 worker**：worker 只做计算，返回纯数据；主 worker 负责按签名读写
   `cachedBySigAsync`（见 `docs/CACHE-INVALIDATION.md`）。这样避免"每个 worker 一份缓存"导致
   命中率被打散、失效口径变复杂。
4. **IPC 要便宜**：`worker_threads` 的 `postMessage` 用结构化克隆。**严禁把 data URL / base64
   大字符串搬过去**（图片类查询不进池就是这个原因：它们的返回值可能几 MB）。
   只搬"小结果"（词频表、统计数字）。
5. **棘轮会继续管着**：新增文件要过 `function-size-ratchet`、`query-db-lifetime`（连接纪律）、
   1000 行单文件棘轮、幻影引用守卫（注释里引用的路径必须存在 —— 本文档的路径都真实存在）。

## 3. 分期计划（每一期都要能独立验收，不许半成品）

**第 1 期：先量 IPC 与序列化成本（不接业务）**
- 造一个最小 worker：收 `{method, args}`、返回一个**构造出来的**小对象（不发数据库）。
- 量：往返延迟、每 worker 启动时间、每 worker 常驻内存。
- 门槛：往返延迟必须 **< 5ms**（否则几十次查询的 IPC 开销就吃掉收益）。

**第 2 期：只接一个方法（`getWordCloud`，当前最大单点 899ms）**

先决条件（第 35 轮查清的**构建层**问题）：后端目前是**单入口打包** ——
`scripts/build-wechat-bundle.js` 用 esbuild 的 `entryPoints: [entry]` + `outfile: lib/index.js`。
而 `new Worker(url)` 需要一个**真实存在的文件**，所以第 2 期必须先在构建层做一个选择：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 构建改为多入口（`outdir` + 第二个 entry，如 `lib/query-worker.js`）；运行时 `new Worker(new URL('./query-worker.js', import.meta.url))` | 要改构建脚本；**会触发 `bundle-size-report` 这类账本守卫**，需按守卫允许的方式登记第二个产物并写明理由；`asar` 打包路径要确认 worker 文件在包内可寻址 |
| B | `new Worker(codeString, { eval: true })`（worker 源码作为字符串内联进 bundle） | 不用加文件，但 worker 内部**无法 import 打包好的模块**，只能自己重写取数逻辑 ⇒ 会形成第二份实现（**不接受**：两份逻辑必然漂移） |
| C | 多进程（`child_process` + IPC） | 与 A 相比多了进程启动/内存成本，且本仓在受限环境下对"管道捕获 stdio"有已知限制 ⇒ 不作为首选 |

⇒ 第 2 期的第一步是**方案 A 的构建改造**（不动取数逻辑），确认 `lib/query-worker.js` 能被
主进程正确加载、在 asar 下也能寻址；第二步才把 `getWordCloud` 接进去。

- 池里只放它；主 worker 保留缓存与签名逻辑。
- 开关：`SUPERTIME_QUERY_POOL=<N>`，默认 `0`（**行为必须与现在完全一致**）。
- 验收（真机，同一份数据副本，与串行对照）：
  - 单个查询的 wall 不得变差（> +10% 即失败，IPC/启动会吃掉收益）；
  - **四条重查询并发时**：`wall(串行 1345ms) → 应 ≤ 1000ms`（理论上限 899ms，留 10% 余量）；
  - 结果**逐字段与串行一致**（词频表逐词逐序比对）；
  - 16 面板巡检 `≤1s 的页签` 不下降、`轻调用也慢` 仍为 0；
  - 每 worker 常驻内存与句柄数（决定池大小 N；第 34 轮探针漏测了 rss，这里补上）。
- **门槛：实测加速比 < 1.3× 就停手并撤掉**（这类改动换来的复杂度必须值回票价）。

**第 1 期实测结论（第 34 轮，已通过）**：往返延迟最坏 **1.10ms**（1000 词返回值）、
worker 启动 **~14–16ms**、真实 worker（含打开只读库）往返中位 **0.00ms** ⇒
设计里"< 5ms"的门槛以很大余量通过 ⇒ **可以进第 2 期**。

**第 3 期：按第 2 期的实测数据决定是否扩到 `getStorageStats` / `getOverviewInsights` / `getOverview`。**

## 3.5 更便宜的替代方案（先试这个）：短作业优先排队

第 37 轮量到一件事，它改变了收益的排序：`getStorageStats` **自身只要 133ms**，
但在巡检里出现 **1336ms** —— 因为同一个单线程 worker 里前面压着词云/洞察等重查询。
也就是说，**剩下的大头是"排队"，不是"算得慢"**。

⇒ 在动 worker 池（架构级）之前，先试一个**不需要架构改动**的办法：

- **做法**：worker 收到请求后**先缓冲一个极短的窗口**（例如 4–8ms，`SUPERTIME_SJF_WINDOW_MS` 可调），
  把窗口内到达的请求按**已知成本档位**排序后再执行：轻的（`getOverview`、`getCalls`、
  `getLedger`…）先跑，重的（`getWordCloud`、`getStorageStats`、`getOverviewInsights`）后跑。
- **为什么有效**：轻查询各自只有几十毫秒，先跑完能让**多个面板几乎同时出内容**；
  重查询本来就要几百毫秒，晚 20ms 开始对用户无感。收益形状与线程池相同（总和→最慢），
  但**没有线程、没有第二份连接、没有 IPC**。
- **绝对不能碰的**：**写类/有副作用的方法永不重排**（`saveWechatConfig`、导出、备份、
  解密、建索引…），它们的相对顺序必须原样保持。判据要**白名单**（只对"确认无副作用且可重放"的
  只读查询启用），而不是黑名单。
- **可能被守卫拦**：worker 的请求处理路径如果有"输入顺序"相关的守卫/用例，先读清楚再改。
- **门槛（与线程池同一套）**：四条重查询并发 `wall ≤ 1000ms`；轻查询的 p95 不得变差；
  巡检 16 面板 `≤1s` 不下降；**收益 <1.3× 就撤**（同样一句话：复杂度要值回票价）。
- **预测**：如果排队确实是主因，这个方案能拿到的收益**接近**线程池的上限（446ms/33% 那一档），
  却便宜得多 ⇒ **先试它；不行再上 worker 池**。

## 4. 明确不做的事


- 不把**图片/头像/封面**类查询放进池：返回值太大，序列化成本会超过并行收益。
- 不让 worker 直接读写结果缓存：缓存口径只能有一处（主 worker），否则失效逻辑会分裂成两套。
- 不在同一个 worker 内用 `Promise.all` 假装并行：同步 SQLite 下它只是排队（这是第 32 轮量出来的）。

## 5. 回退与观测

- 开关：环境变量 `SUPERTIME_QUERY_POOL=<N>`（默认 `0` = 关闭，行为与现在**完全一致**）；
  这样出问题可以一行回到现状，也让"有/无池"的 A/B 测量成为可能。
- 观测：沿用现成量具 —— `SUPERTIME_SLOW_CALL_MS`（逐接口时间线）、
  `SUPERTIME_CACHE_TRACE=1`（缓存命中）、以及 `working/measure-real-load.mjs`（页面级）。
